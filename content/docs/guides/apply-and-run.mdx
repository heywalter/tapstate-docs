Use this guide for CLI authoring and automation on a **self-hosted server**. For the web workflow, see
[Build a pipeline](/docs/guides/build-a-pipeline). The CLI examples cover
the v0.8 client and self-hosted authentication. The CLI cannot use a Cloud browser session to apply these files.

`apply` validates resource files and stores them on the server. Lifecycle
commands then request the state that the runtime converges toward. Applying a
changed pipeline does not restart its active run.

## Before you begin

- Validate the workspace locally.
- Register the required connector JARs.
- Apply and test source and target connections from the server environment.
- Use a non-production data set for the preview.

See [Register and test connectors](/docs/guides/register-connectors) for the preceding sequence.

## Apply the workspace

Start an authenticated session in the workspace:

```bash
tapstate -w work
```

```text
connect http://127.0.0.1:8080
login admin
apply
```

With no operand, `apply` sends the workspace as one batch. To apply one file or directory:

```text
apply source/orders_source.tap.yml
```

The server reparses and validates each draft. The result reports:

- `CREATED` for a new artifact;
- `UPDATED` when canonical content changed;
- `UNCHANGED` when the stored content hash already matches.

Some checks require the source's discovered schema and therefore run only on
the server. If apply returns `dsl.upsert-needs-key`, every selected source table
written with the default `upsert` mode needs a discovered primary key. Discover
the source again and select keyed tables, or use `append` only when the delivery
is insert-only. A unique index or `tables[].pk` does not satisfy this runtime
check.

Confirm the server-held resources:

```text
ls
get orders_source
get orders_to_operational_state
```

Local files remain authoring input; connected `get` and `ls` show the stored
resources. Source configuration is omitted from generic artifact output to
protect credentials; this output is not a complete configuration backup.

## Start the pipeline

```text
start orders_to_operational_state
status orders_to_operational_state --watch
```

Before accepting `start`, a v0.8 server runs read-only checks against the
applied revision and the intended load. Once those checks allow it, `start`
writes a `RUNNING` intent. `status --watch` reports observed runtime state,
which can lag the command briefly.

Verify data at the destination. A lifecycle command succeeding proves that the intent was accepted, not that rows arrived.

For Cloud Web confirmations, see [Review start checks](/docs/guides/build-a-pipeline#review-start-checks).
Those controls share the same start-check concepts as these self-hosted CLI commands.

## Start checks

These checks require the v0.8 server and matching clients. See
[upgrade requirements](/docs/releases/v0.8#before-upgrading).

Start checks apply to explicit starts from the Web, CLI, REST, and MCP. Read
the report before deciding how to continue:

| Finding | Effect |
|---|---|
| `PASS` | The check allows the start. |
| `WARN` | The start may continue, but the reported condition needs review. An unavailable or timed-out check is not a passed check. |
| `CONFIRM` | Answer the offered question before the server accepts the start. |
| `BLOCK` | Correct the condition; answering other questions cannot override the refusal. |

### Existing rows in a target

A new full load copies rows that exist at the source now. It cannot remove
rows deleted from the source while the pipeline was stopped if those rows are
kept in the target. The `target-not-empty` check asks what to do when the
configured `on_full_load: append` policy would keep a nonempty target:

- **Keep** acknowledges the existing rows and starts with the current policy.
- **Clear**, when offered, removes the target's existing rows before the full
  load and saves `on_full_load: clear` on the writing element, which also
  changes what later full loads do. Use it only when all affected target data
  may be removed.

A target configured with `on_full_load: fail` blocks the start if nonempty. An
empty target, one already configured to clear, a resume, or a CDC-only run
does not ask this question. If the writing element comes from a shared View or
Serve definition, the start offers **Keep** only; update the shared definition
separately if its policy should change.

In the CLI, inspect checks without starting:

```text
start orders_to_operational_state --checks-only -o json
```

It exits successfully only when nothing requires confirmation or blocks the
start. At a terminal, pressing Enter, canceling, or reaching end of input
leaves the pipeline unchanged. In a script, pass an offered decision explicitly:

```text
start orders_to_operational_state --decide target-not-empty=keep
```

This example retains existing rows. `-y` answers remaining questions by
continuing as configured (`on_full_load`); it does not mean “clear every target”
and does not override a block. See [Start-check options](/docs/reference/cli#start-check-options).

The server re-evaluates checks on each attempt. If the definition changes,
refresh the report before answering. Automatic recovery from retained state
does not ask these questions or clear targets. A start request whose response
was lost should be checked through `status` before another attempt.

## Lifecycle transitions

| Command | Legal starting state | Target state | Progress behavior |
|---|---|---|---|
| `start` | `NEW`, `STOPPED`, `COMPLETED` | `RUNNING` | Starts at the latest applied revision, using retained progress when available. |
| `pause` | `RUNNING` | `PAUSED` | Retains the current revision and in-run progress. |
| `resume` | `PAUSED` | `RUNNING` | Continues from retained progress. Compatible edits can rebuild the run at the latest revision. |
| `stop` | `RUNNING`, `PAUSED`, `FAILED`, `COMPLETED` | `STOPPED` | Asks for confirmation, then clears this pipeline's recovery position and operator state. |
| `stop --keep-state` | `RUNNING`, `PAUSED`, `FAILED`, `COMPLETED` | `STOPPED` | Retains recovery positions and operator state for the next run. |

An illegal transition returns `lifecycle.illegal-transition`. If edits cannot
reuse a paused pipeline's state, `resume` returns
`lifecycle.incompatible-revision`. Review the change and decide whether the
next run can retain state or needs a full reload.

After whole-cache recovery, affected pipelines remain stopped and require
separate [full-rebuild confirmation](/docs/manage/storage-recovery). The
ordinary `start` and `resume` commands cannot bypass that requirement, even when
the pipeline's visible state is `STOPPED`.

A lifecycle request can be accepted before the runtime finishes the transition.
Before starting again, wait for the status API's `observedState` to reach
`STOPPED`.

Plain `stop` clears state. Use `--keep-state` when you intend to continue from
retained progress. To accept clearing in a script, use `stop <id> -y`.

Clearing leaves this pipeline without a recovery position. Shared capture
state is cleared only when its last dependent pipeline clears state, so
stopping one consumer does not guarantee a full source reload. Neither choice
deletes existing destination rows; reconcile them with your chosen write
strategy. See [State and storage](/docs/concepts/storage).

Recover a failed pipeline deliberately:

```text
logs orders_to_operational_state
stop orders_to_operational_state --keep-state
start orders_to_operational_state
```

Do not start directly from `FAILED`. Keeping state does not repair an invalid
recovery position; investigate recovery diagnostics before retrying or clearing
progress.

## Completed snapshot loads

A snapshot-only run reaches `COMPLETED` after the graph drains and its target
writes are confirmed. Final progress remains visible and runtime resources are
released. Snapshot-and-CDC and CDC-only runs remain continuous and do not
complete just because their initial snapshot finished.

For the Cloud Web restart behavior, see
[Completed snapshot restarts](/docs/guides/build-a-pipeline#completed-snapshot-restarts).
When testing restarts or **Clear** against an existing destination, verify actual
target rows on an independent test target rather than relying on `FULL_LOAD` or
`COMPLETED` status alone.

## Verify the outcome

Use all three evidence types:

1. `status` reaches the expected state;
2. `metrics` and `logs` show active work without unresolved errors;
3. source and destination queries show the expected snapshot and later insert, update, and delete behavior.

The server retains recovery positions and durable operator state. A restart can
resume from a retained position and replay records; it does not provide
exactly-once delivery. Snapshot-only reads may restart their load. Retaining a
checkpoint is safe only while its corresponding operator state is also retained.
See [State and storage](/docs/concepts/storage) and [Configure a cluster](/docs/guides/cluster).
