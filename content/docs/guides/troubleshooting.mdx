Start by identifying which layer produced the failure. A resource-file error, a connection failure, and incorrect destination data require different evidence and different fixes.

## Read the command result

tapstate commands use these exit codes:

| Code | Meaning |
|---:|---|
| `0` | Success |
| `1` | A coded domain diagnostic or refused operation |
| `2` | Invalid command usage |
| `3` | Unavailable in this context, not connected, or not implemented |

Use `tapstate --help` to inspect the commands in your installed version. In
`v0.2.0`, use `tapstate help <command>` or `tapstate <command> --help` for a
command's operands and options.

Successful data is written to standard output; usage and diagnostics are written to standard error. Preserve both streams and the exit code when collecting evidence.

## Identify the failing layer

| Layer | Typical evidence | What it can establish |
|---|---|---|
| Documentation and resource shape | Page reference, YAML diff, schema diagnostic | Whether the resource follows the documented contract |
| Connector contract | Connector ID, mode, field names, preparation guide | Whether the requested role and configuration are declared |
| Deployment and connectivity | Runtime logs, network test, authentication response | Whether this deployment can reach and authenticate to the system |
| Data movement | Checkpoints, source and target samples, record counts | Whether Snapshot, CDC, transforms, and writes behave correctly |

Do not use evidence from one layer as proof of another. A valid resource file is the starting point; connectivity and data movement still need to be verified in the environment where the connection runs.

## Check the workspace first

Run the validation command supplied with your tapstate environment before investigating the external system:

```bash
tapstate validate --workdir tapstate-work
```

Review the filename, location, diagnostic code, message, and suggested fix. Correct one layer at a time, then validate again.

### Unknown field or invalid value

- Confirm the connector ID and exact field spelling in its [Reference](/docs/connectors) section.
- Remove fields copied from an upstream UI or another connector version unless the tapstate contract exposes them.
- Check whether the field is conditional on another value, such as authentication method or storage type.

### Invalid mode

- Use only modes shown on the connector page.
- Do not add `cdc` because the underlying database supports a transaction log.
- A target-only connection does not need a source read mode.

### Missing or unresolved reference

- Confirm that pipeline references match resource IDs exactly.
- Keep every referenced resource in the selected work directory.
- Check for renamed files whose internal `id` did not change with the filename.

### Row-expression schema and type errors

These checks apply to `filter` expressions and computed `map` fields that read
`after.<field>` or `before.<field>`:

- `dsl.row-expression-needs-discovery` means at least one source that can reach
  the expression has no discovered schema. Apply the source connection by
  itself, run `discover-schema <source-id>`, then apply the pipeline or complete
  workspace again.
- `dsl.row-expression-type-unsupported` means the referenced column cannot be
  represented in CEL without losing information. Carry the column through
  unchanged, or compute from a compatible column instead.
- `dsl.row-expression-type-unknown` means the discovered schema has no resolved
  type for the referenced column. Remove that reference or use a column with a
  declared type.

These diagnostics restrict computation, not pass-through. A column that cannot
be computed losslessly can still flow through a `map` when no computed rule
reads it.

## Troubleshoot the local demo

The [local demo](/docs/overview/quickstart-online) prints the MongoDB row count
after it requests that the pipeline start. A healthy server or a
`sync_orders running` line does not establish that data moved. Treat the demo
as successful only when connector registration and schema discovery complete
without a refusal and the script prints `the target now holds 5 rows`.

The `v0.2.0` script can continue after a refused command or a lower target
count, so inspect the complete output and target data instead of relying on its
exit code alone.

### Docker is unavailable

```bash
docker info
docker compose version
```

Start Docker and confirm the Compose plugin is available. The demo needs to pull and run MySQL 8.0, MongoDB 7.0, and the tapstate server.

### A container is unhealthy or stopped

```bash
docker compose ps
docker compose logs --tail=200 mysql mongo server
```

Fix port conflicts or local resource pressure before rerunning. Keep passwords and tokens out of shared log bundles.

### The five-row result does not appear

Check the source and target independently:

```bash
docker compose exec mysql mysql -uroot -psecret appdb \
  -e "SELECT COUNT(*) AS source_rows FROM orders;"

docker compose exec mongo mongosh --quiet \
  'mongodb://mongo:27017/warehouse?directConnection=true' \
  --eval 'db.orders.countDocuments({})'
```

If MySQL has five rows and MongoDB does not, enter the CLI REPL and collect pipeline evidence:

```bash
./tapstate -w work
```

```text
connect http://127.0.0.1:8080
login admin
status sync_orders
metrics sync_orders
logs sync_orders
```

Enter the password stored in the local `.env` file. Do not paste it into a shell command or diagnostic bundle.

### A rerun reports an illegal lifecycle transition

The script preserves generated assets and may encounter a pipeline that is already running after a partial or completed attempt. Inspect `status` first. For a clean local reset:

```bash
docker compose down -v
sh quickstart.sh
```

`down -v` permanently removes the demo's local MySQL and MongoDB volumes. It does not remove files in the demo directory.

### A connected command returns exit code 3

The command was invoked without a server connection, or the verb is reserved
but not implemented. Start an interactive session and run `connect` and `login`,
or seed a one-shot command with `-c` and `-u`. For automation, pass the password
through `TAPSTATE_PASSWORD` instead of `-p` so it is not exposed in shell history
or the process list.

## Check external-system preparation

If the resource shape is valid but a deployment cannot connect or discover objects:

1. Confirm DNS, port, routing, firewall, and allowlist rules from the runtime host.
2. Authenticate with the same account outside tapstate when a safe vendor tool is available.
3. Recheck source and target privileges separately.
4. Verify the database, schema, warehouse, tenant, topic, bucket, or API scope.
5. Follow the connector page's mode-specific preparation path.

For TLS and connection testing, use only the fields and workflow supported by the tapstate environment you operate. Do not copy certificate fields or test commands from another product.

## Check Snapshot or CDC behavior

For an incomplete Snapshot:

- compare the selected object list with source discovery;
- check table-pattern and include/exclude rules;
- compare counts at a stable source boundary;
- inspect unsupported objects and data types in the connector limitations.

For CDC that stops or falls behind:

- check log, WAL, Oplog, snapshot, or broker retention;
- confirm that the saved recovery position still exists;
- verify replication or change-capture privileges;
- inspect long transactions and source-side cleanup jobs;
- test insert, update, delete, stop, and resume in staging.

## Check target correctness

- Confirm that updates and deletes have a stable key.
- Distinguish append behavior from key-based update behavior.
- Review automatic table creation and schema-change policy.
- Check target constraints, column types, partitioning, and conflict handling.
- Design downstream processing to tolerate duplicate delivery unless your deployment documents a stronger delivery guarantee.

## Interpret observations carefully

- `status` and `metrics` report observed state and may lag a lifecycle command briefly.
- `status --watch` and `logs --follow` continue until you press <kbd>Ctrl</kbd>+<kbd>C</kbd>.
- Logs are node-local in the preview and are not a durable audit history.
- `snapshot` can report that no snapshot is available. Confirm source and target records instead of treating that response alone as proof of success or failure.

## Collect a useful diagnostic bundle

Before escalating, collect:

- tapstate version and deployment type;
- connector ID, role, and mode;
- redacted resource files;
- exact command and exit code;
- complete diagnostic or runtime error;
- relevant connector-page URL;
- external-system version and topology;
- timestamp and smallest reproducible dataset;
- expected and observed records.

Remove passwords, tokens, private keys, and customer data before sharing the bundle.
