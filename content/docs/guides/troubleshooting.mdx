Start by identifying which layer produced the failure. A configuration error,
a connection failure, and incorrect destination data require different evidence
and different fixes.

For CLI exit codes, `.tap.yml` workspace validation, the local Docker quickstart,
or self-hosted server errors, see [Troubleshoot self-hosted deployments](/docs/self-hosted/troubleshooting).

## Start with the Cloud workflow

| Symptom | First checks |
|---|---|
| The expected organization or Cluster is missing | Check the signed-in account and selected [organization](/docs/manage/organizations). Ask its owner to confirm access. |
| Checkout returned but the Cluster is not ready | Check subscription status in [Billing](/docs/manage/billing) and resource status in **Clusters**. Do not infer provisioning success from payment alone. |
| A source or Atlas connection fails | Check the [Cluster outbound IP](/docs/manage/clusters#prepare-network-access), network allowlists, endpoint, credentials, and connector permissions. Keep TLS verification enabled. |
| The Cluster asks for storage setup | Open **Connect Atlas**, add the Cluster's outbound IP to Atlas, and select **Connect** to check and save settings ([Connect storage](/docs/quickstart#2-connect-storage)). |
| Cache setup reports an occupied database, even with zero documents | Select **Use suggested name** when offered or enter a new empty database name; any existing collection blocks first-time setup. Do not delete existing collections just to reuse a name. |
| Cache setup cannot list collections | Ask the database administrator to grant metadata inspection access; the failure does not establish whether the database is empty. |
| Sign-in is interrupted during first initialization | Reopen the same Cluster from Cloud and check the original setup. Do not reset storage or create another Cluster. |
| Saving storage timed out or initialization stopped refreshing | Reopen the same Cluster and check its original operation. A lost response does not mean the settings were not saved. |
| The Cluster opens, but the default destination check failed or is unverified | Check the [default destination result](/docs/manage/clusters#check-the-default-destination) and its database access. Do not repeat installation. |
| Saved storage is not yet active | Check the original setup status and use **Retry storage activation** only when offered. Keep the original Cluster and database names; Cloud setup does not require a local installation directory. |
| An alert remains active after a repair | Check its latest observation and recovery evidence in [Alerts](/docs/manage/alerts#inspect-an-alert). Missing observations do not confirm recovery. |
| An alert appeared but no notification arrived | Check the alert, any silence, and [notification delivery](/docs/manage/alerts#interpret-delivery-results). Cloud manages external routing; acceptance does not confirm recipient delivery. Keep the Cloud event ID for support. |
| Storage is unavailable | Restore access to the original database, credentials, and trust settings. Use [runtime storage recovery](/docs/manage/storage-recovery) only for the supported lost-state case. |
| Storage recovery finished but pipelines are stopped | Review and confirm each affected pipeline's full rebuild separately. Storage recovery does not automatically restart pipelines. |
| Pipeline edits stay unsaved or saving fails | Read the save error and keep the page open until it is resolved. A saved draft is not a published or running pipeline. Follow [Build a pipeline](/docs/guides/build-a-pipeline#2-create-a-draft). |
| The start button shows a busy indicator | Wait for the current request or start-check dialog. The indicator includes publication and does not establish that the pipeline is running. After a lost response, inspect the existing pipeline's status before retrying. |
| Start published the configuration but the pipeline did not run | Resolve or confirm the start checks, then inspect Monitoring. Publishing and starting are separate results; do not clear target data just to retry. |
| Monitoring shows a draft or logs are empty | Save and start a valid pipeline before expecting runtime observations. An empty log view alone is not evidence of health. |
| Views reports unresolved outputs or omits an expected collection | Check the named pipeline's source selection, discovered schema, and referenced definitions. Refresh after correcting them; other listed outputs do not prove the inventory is complete. See [output locations](/docs/reference/rest-api#locate-a-materialized-collection). |
| Monitoring says Sync healthy but the data has not been checked | Compare known output records. For stable direct mappings, run [Data validation](/docs/guides/validate-pipeline-data). Sync health is not a data comparison. |
| Data validation is blocked or incomplete | Check the supported mapping, saved keys, and original run state. Follow [Resolve a blocked check](/docs/guides/validate-pipeline-data#resolve-a-blocked-check); an empty partial report does not mean the data matches. |
| A pipeline runs but data is missing or stale | Compare known source and destination records; check discovered keys, capture mode, logs, and acknowledged progress. Follow [Observe a pipeline](/docs/guides/observe-a-pipeline). |
| The AI assistant asks you to select an input or correct a proposal | Choose the source and input table, check discovered schemas, and continue the conversation with the reported issue. Review [Build with AI](/docs/guides/build-a-pipeline#build-with-ai) before applying changes. |
| The AI provider check or generation fails | Check the endpoint, model, and saved key. A connection check does not save provider settings. Resolve a draft save conflict before retrying generation. |
| Trial dates disagree between setup and Billing | Follow [Trial dates do not match](/docs/manage/billing#trial-dates-do-not-match); do not infer an extended trial from a conflicting display. |
| Checkout timed out, was submitted twice, or Billing has no price | Follow the [Billing FAQ](/docs/manage/billing#billing-faq) before starting another subscription. |

For support, record the affected organization and Cluster, the action, time
including time zone, displayed status, and a short error description. Remove
credentials, connection URIs, payment details, and customer data from evidence.

## Resolve start checks

In Cloud, review the Web start report before changing state. A refused start
does not establish that a new run began.

- `lifecycle.start-needs-confirmation`: review the finding, affected target,
  actions, and saved full-load policy. Choose explicitly; **Clear** also saves
  that policy for future full loads.
- `lifecycle.start-blocked`: correct the blocking condition, then request fresh
  checks. Confirmation flags do not override it.
- `lifecycle.pipeline-not-runnable`: resolve the pipeline's current lifecycle
  state before requesting another start.

For REST, use the fresh report's content hash. HTTP `428` can mean a
missing or malformed required precondition; `412` means the resource changed.
Reload and review rather than replaying an old answer. A timeout can leave the
outcome uncertain: inspect status before retrying a state-changing request.
See [Start checks](/docs/guides/build-a-pipeline#review-start-checks) and
[REST start decisions](/docs/reference/rest-api#answer-start-checks).

### Unwind keys, indexes, and before images

| Diagnostic | What to check |
|---|---|
| `connector.target-identity-check-failed` | Target reachability and metadata permissions, complete matching keys, and incompatible unique indexes. An unreadable index report is not a successful identity check. |
| `dsl.unwind-needs-an-element-key` | Set `element_key` for object elements or `include_array_index` for ordinal identity. |
| `dsl.unwind-needs-an-upsert-target` | Use a keyed upsert destination for the expanded result. |
| `dsl.unwind-column-already-exists` | Rename the preserved source identity or index field to avoid the reported collision. |
| `transform.unwind-needs-a-complete-before-image` | Configure complete source before images so updates and deletes can retract earlier expanded rows. |
| `transform.unwind-rows-share-a-key` | Expanded elements share one key. Choose an element key that identifies each element; otherwise writes can replace one another. |

Changing an identity field on a populated target does not migrate existing
rows. Review [Unwind](/docs/reference/transforms#unwind) before changing keys or
indexes, and test in an independent destination.

### A filtered row remains in the target

For an update that stops matching, check whether the source supplied the full
before image required to evaluate the previous row. For a source delete, check
whether the expression handles `op == 'd'` using `before` instead of relying on
an empty `after`. Compare the source event and the actual keyed target row.
See [Maintain a filtered result](/docs/reference/transforms#maintain-a-filtered-result).

### A filtered row does not return after matching again

In Cloud, a MySQL row removed from a filtered managed View can
remain absent when a later update matches again. Compare the source row and
keyed target row; `RUNNING` alone does not prove the result is complete. See
[the known limitation](/docs/reference/transforms#maintain-a-filtered-result)
before relying on this path.

### Editing a connection changes authentication

In structured edits, omitting a saved secret for the same connector retains it.
Supply a new value to replace it, or use `clearSecrets` to remove it explicitly;
`null` is refused. A redacted response is not a credential backup. Check the
connector ID and the reported configured secret paths before retrying. See
[Edit saved credentials](/docs/reference/rest-api#edit-saved-credentials).

## Identify the failing layer

| Layer | Typical evidence | What it can establish |
|---|---|---|
| Documentation and resource shape | Page reference, configuration diff, schema diagnostic | Whether the configuration follows the documented contract |
| Connector contract | Connector ID, mode, field names, preparation guide | Whether the requested role and configuration are declared |
| Deployment and connectivity | Runtime logs, network test, authentication response | Whether this deployment can reach and authenticate to the system |
| Data movement | Checkpoints, source and target samples, record counts | Whether Snapshot, CDC, transforms, and writes behave correctly |

Do not use evidence from one layer as proof of another. Valid settings or
resource files are the starting point; connectivity and data movement still need
to be verified in the environment where the connection runs.

## Check external-system preparation

If the settings are valid but a deployment cannot connect or discover objects:

1. Confirm DNS, port, routing, firewall, and allowlist rules from the runtime host (including the [Cluster outbound IP](/docs/manage/clusters#prepare-network-access) in Cloud).
2. Authenticate with the same account outside tapstate when a safe vendor tool is available.
3. Recheck source and target privileges separately.
4. Verify the database, schema, warehouse, tenant, topic, bucket, or API scope.
5. Follow the connector page's mode-specific preparation path.

For TLS and connection testing, use only the fields and workflow supported by the tapstate environment you operate. Do not copy certificate fields or test commands from another product.

## Check Snapshot or CDC behavior

### Table selection errors

Table selectors are resolved when the runtime builds the pipeline. Validate the
configuration first, refresh the source schema in **Data Sources**, and save
your updates before starting again.

| Diagnostic | What it means | What to do |
|---|---|---|
| `actuation.source-schema-not-discovered` | The source needs a discovered schema to expand an omitted `tables` field or a regex selector. | Refresh schema in **Data Sources**, then save and start the pipeline again. |
| `actuation.source-table-not-discovered` | A named table is not in the source's current discovered schema. | Discover the source again and use the exact discovered table name. |
| `actuation.source-table-selection-empty` | The selectors resolve to no tables. This includes an empty list, a non-matching regex, or an omitted selector with no discovered tables. | Supply a literal name or a regex that matches at least one discovered table. |
| `actuation.source-table-ambiguous` | More than one pipeline source selects the same bare table name. | Where the pipeline names that table, replace the bare name with `source_id.table`. |
| `actuation.source-table-regex-invalid` | A table regex is not valid Java regular-expression syntax. | Correct the regex, keep it quoted when it contains YAML flow indicators, then update the pipeline again. |
| `actuation.source-table-spec-unsupported` | A table object includes fields that the current preview capture path does not execute. | Use a literal or regex selector, or an object with `name` only. |

For an incomplete Snapshot:

- compare the selected object list with source discovery;
- check table-pattern and include/exclude rules;
- compare counts at a stable source boundary;
- inspect unsupported objects and data types in the connector limitations.

For CDC that stops or falls behind:

- check log, WAL, Oplog, snapshot, or broker retention;
- confirm that the saved recovery position still exists;
- verify replication or change-capture privileges;
- inspect long transactions and source-side cleanup jobs;
- test insert, update, delete, stop, and resume in staging.

### PostgreSQL reports an active replication slot

If a capture failure says that its replication slot is already active, check
`pg_replication_slots.active_pid` and the owning database session. Stop the
affected pipeline and confirm that the previous reader has disconnected before
starting another reader. Do not drop a slot that an existing pipeline needs.

After recovery, verify a new source change in the target. A `RUNNING` status
alone does not prove that PostgreSQL CDC resumed. See the
[replication-slot lifecycle](/docs/connectors/postgresql#replication-slots-and-recovery).

### Recovery is refused

`capture.recovery-log-gap` means retained source history no longer contains a
change the consumer needs. `capture.recovery-progress-unproven` means the
retained checkpoint cannot establish a safe continuation.

Keep the full diagnostic, then check source log retention and compare source
and target records before clearing pipeline state or rerunning from scratch.
Review the target write strategy as well: clearing one pipeline does not erase
completed-table history retained by a shared mining chain. See
[Resume or rerun](/docs/concepts/capture-modes#resume-or-rerun).

## Check target correctness

- Confirm that updates and deletes have a stable key.
- Distinguish append behavior from key-based update behavior.
- Review automatic table creation and schema-change policy.
- Check target constraints, column types, partitioning, and conflict handling.
- Design downstream processing to tolerate duplicate delivery unless your deployment documents a stronger delivery guarantee.

### Schema and document size diagnostics

| Diagnostic | What it means | What to do |
|---|---|---|
| `io.document-too-large` | A pipeline model or schema history entry exceeded MongoDB's 16MB document size limit. | The state store is healthy; retrying will not resolve the issue. Reduce the volume of schema history or wide table models tracked under the affected ID. |
| `io.schema-write-contention` | Schema discovery failed to publish because its writer lease was reclaimed or concurrent discovery altered the record. | Wait for active discovery tasks to complete, then retry **Refresh schema**. |

## Collect a useful diagnostic bundle

Before escalating, collect:

- Cloud organization, Cluster name, and **Runtime version** from **Clusters**;
- pipeline ID, **Monitoring** figures, and **Logs** lines;
- connector ID, role, and mode;
- complete diagnostic or runtime error;
- relevant connector-page URL;
- external-system version and topology;
- timestamp and smallest reproducible dataset;
- expected and observed records.

Remove passwords, tokens, private keys, and customer data before sharing the bundle.

## Pipeline and transform diagnostics

### Row-expression schema and type errors

These checks apply to `filter` expressions and computed `map` fields that read
`after.<field>` or `before.<field>`:

- `dsl.row-expression-needs-discovery` means at least one source that can reach
  the expression has no discovered schema. Open the source in **Data Sources**,
  select **Refresh schema**, then save or publish the pipeline again.
- `dsl.row-expression-type-unsupported` means the referenced column cannot be
  represented in CEL without losing information. Carry the column through
  unchanged, or compute from a compatible column instead.
- `dsl.row-expression-type-unknown` means the discovered schema has no resolved
  type for the referenced column. Remove that reference or use a column with a
  declared type.

These diagnostics restrict computation, not pass-through. A column that cannot
be computed losslessly can still flow through a `map` when no computed rule
reads it.

### Upsert source has no discovered primary key

`dsl.upsert-needs-key` is a server-side validation diagnostic. It means a
selected source table is being written with `upsert`, but its discovered schema
has no primary key. The diagnostic identifies the affected `source`, `table`,
and resource `path`.

Refresh the source schema and select a table with a primary key. A unique
index, a target-side key, or `tables[].pk` does not satisfy this runtime check.
Use `append` only when the delivery is insert-only and source updates and
deletes do not need keyed handling.

### Dotted field names in document stores

`schema.column-name-reads-as-a-path` is an advisory warning. It indicates that a
source table column contains a dot (such as `price.usd`) and is being mapped to
a document store like MongoDB or MongoDB Atlas.

Document stores write literal dotted keys, but query paths interpret dots as
navigation into nested documents, causing direct field queries to return empty
results and preventing index creation. To resolve this, rename the column in the
source database or insert a `map` transform step to alias the dot to an
underscore before writing to the destination.

### Nest and Join transform diagnostics

| Diagnostic | What it means | What to do |
|---|---|---|
| `nest.reference-tracking-requires-before-image` | An update on a stream behind a pointed-at embed carried no before image, preventing the engine from unlinking the row's prior reference. | Configure the stream's source to send before images (such as PostgreSQL `REPLICA IDENTITY FULL`). Without before images, unlinked rows cannot be reclaimed. |
| `nest.key-change-tracking-requires-before-image` | An update on a stream tracking key changes carried an earlier row image missing key columns. | Configure the source to send whole row images rather than minimal ones (such as MySQL `binlog_row_image=FULL` or PostgreSQL `REPLICA IDENTITY FULL`), or turn key change tracking off for that stream. |
| `actuation.join-output-key-not-published` | A pipeline `join` step writes to an `upsert` sync target, but its SELECT list does not directly project all primary-key columns of the driving fact table. | Project each driving fact table primary-key column directly in the SELECT list (aliases such as `o.id AS order_id` are permitted). |
| `actuation.join-source-not-declared` | A `join` SQL query references a table alias that was not declared in the step's `from` mapping. | Align the SQL table alias with one declared in the step's `from` map. |
| `actuation.join-source-key-missing` | The driving fact table in a `join` step has no discovered primary key. | Define a primary key on the source table, refresh schema discovery, and restart the pipeline. |
| `dsl.join-sql-unsupported` | The join SQL statement uses unsupported clauses (such as `WHERE`, `GROUP BY`, `HAVING`, subqueries, or non-equality conditions). | Rewrite the SQL within the supported subset: one SELECT combining tables via equality associations directly between driving fact and dimension sources. |
| `engine.join-dimension-row-displaced` | (WARNING) A second dimension row arrived under an existing join key, displacing the earlier match. | Ensure dimension join keys are unique in the source data, or narrow the source selection. Until resolved, the target will contain fewer rows than described by a relational query. |
