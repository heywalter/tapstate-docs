Open the pipeline in the web application and use **Monitoring** and **Logs**
to inspect its activity. Compare these observations with source and target data
before treating a run as successful.

A draft has no running job to observe. If **Monitoring** asks you to save and
start the pipeline, return to [Build a pipeline](/docs/guides/build-a-pipeline).
A Cluster being **Ready** is separate from a pipeline running or its data being
correct. Missing usage values do not mean zero activity.

For CLI observation commands and Prometheus or OTLP metrics export on a server
you manage, see [Observe self-hosted pipelines](/docs/self-hosted/observe-pipelines).

## Inspect the web application

In **Pipelines**, open your pipeline and select **Monitoring**. Active and
failed runs open there; drafts and stopped pipelines open in **Build**.
Select **Refresh** for new readings. **Last refreshed** records when the page
received data; it is not the time of the underlying runtime observation.

[![Pipeline Monitoring with an out-of-date observation warning, history charts, and key figures](/images/cloud/monitoring.png)](/images/cloud/monitoring.png)

This example shows stale observations. Read the warning before interpreting
the charts; refreshing a page does not make an old runtime observation current.

### Check sync health

Read the status message before interpreting the figures:

| Message | What to check next |
|---|---|
| **Initial load in progress** | Find the loading table below and follow its read and delivery progress. Reading all source rows does not finish the load until the target confirms them. |
| **Not advancing** | Open **Diagnosis details** for the affected tables and suggested next step, then inspect Logs and the target. A table still loading is not diagnosed as stalled just because its frontier has not advanced. |
| **Pipeline failed** | Open Logs and inspect the reported failure code. |
| **Monitoring data is out of date** or **Sync status unknown** | Refresh and check observation age. Missing or old evidence cannot establish current health. |
| **Sync healthy** | The pipeline is running with a fresh diagnosis that found no matching problem. Continue with data checks before treating delivery as correct. |

### Read the key figures

| Figure | Meaning |
|---|---|
| **Newest change delivered** | Age of the newest target-confirmed source event across outputs. It uses the smallest reported event age, so a recent change on one output can coexist with an older reading on another. |
| **Records out** | Latest available per-second rate from target-acknowledged history in the selected time range. The accompanying total and bytes are cumulative counters. |
| **Records in** | Cumulative input records and bytes, not a rate or a count of destination documents. |
| **Initial load** | Target-confirmed tables out of all tables requiring an initial load. Row totals may be estimates; they do not establish completion. |
| **Failures since start** | Shown in place of the Initial load figure when failure counters are nonzero, with their codes. These counters can span run restarts; check the current status and logs before treating them as a new failure. |

Event age grows while a source is idle. It is not end-to-end latency or a
count of queued changes. A missing value is unavailable, not zero.

### Find a table or output

Use **Search tables** to find a source table or destination name. Loading and
stalled tables appear first; larger lists have page controls.

- **Phase** distinguishes waiting, initial load, CDC, and a completed
  snapshot-only load. Initial-load rows remain in that phase while target
  delivery is outstanding.
- **Initial load** shows rows read and an estimated total when available.
  Use the phase as well as the count to check completion.
- **Not advancing for** and **Frontier gap** describe processing progress.
  Compare them with the load phase and diagnosis before acting.
- **Table → target** identifies resolved direct-copy destinations. Nest inputs
  also show their root or embed **Role**; pipelines reading multiple sources
  show a **Source** column. A Nest output's event age can appear separately
  from its input tables.

Tables move through four initial-load stages: `PENDING`, `READING`,
`LANDING` (source reading finished while target delivery is outstanding),
and `LANDED` (target writes confirmed).

### Compare recent history

Choose a time range containing the run. **Records out per second** shows
confirmed delivery; **Time since newest change, per output** separates outputs
that the summary figure combines. When more than five series are available,
select **Show all** to expand them. History requests cover at most 20 outputs,
prioritizing those with the highest current event ages.

Use **View data** for the chart values and **Load more history** when offered.
Gaps and counter resets separate observations; an empty range is not measured
zero throughput. An idle run can have measured zero rates once adjacent
samples establish that nothing was delivered. Samples are recorded every 60
seconds and retained for 15 days by default.

### Inspect supporting details

Expand **Diagnosis details** for the evidence, **What this cannot establish**,
and any **Suggested next step**. **All metrics** groups the available numeric
readings. For Nest pipelines, **Advanced · transform state** shows state
entries, accesses, cold-key share, backfill activity, and state commits,
labelled by step and document path when available; see
[Nest state and cold-layer metrics](/docs/self-hosted/observe-pipelines#nest-state-and-cold-layer-metrics)
for the underlying Prometheus/OTLP and `facts` metric names. These readings
describe processing work, not data correctness.

Status, metrics, snapshot, and history are separate observations. Check their
timing when comparing them.

### Read logs

Select **Logs** to inspect recent runtime messages. Filter by level or time
range, or use **Search**, then select a line to open **Log details**. These
filters narrow the returned tail; they do not search a historical log archive.

[![Pipeline logs with level and time-range filters, search input, and Log details open for the selected row](/images/self-hosted/pipeline-logs.png)](/images/self-hosted/pipeline-logs.png)

#### Interpret progress messages

In Cloud, source capture and target confirmation report separate milestones:

| Message | Meaning |
|---|---|
| `Snapshot read started for table ...` | The source has started reading that table's initial data. |
| `Snapshot read finished for table ... (... events read; awaiting target confirmation)` | Source reading has ended; target writes may still be pending. |
| `Snapshot finished for table ... (target writes confirmed)` | Target acknowledgements have confirmed that table's snapshot on this runtime path. |
| `CDC confirmed for table ...` | Target-confirmed change progress has advanced. These summaries are sampled, not emitted for every row. |

Compare these messages for the same table and run. A confirmed table does not
prove that every table has finished, and source-read counts are not target
document counts after filtering or assembly. Check snapshot progress and
representative target records as well. A quiet log tail alone does not prove
that CDC has stopped.

## Check a View's observation

In **Views**, open the output and review **Event age and observation**.

- **Observed · event age** shows the age of the last target-confirmed source
  event, taking the maximum across this output's inputs. It grows while a
  source is idle; it is not an end-to-end latency or backlog measurement.
- **Measured** is the observation time. **Refreshed** is when the server
  assembled the current response. Refreshing the page does not create a new
  runtime observation.
- **Loading** describes initial-load progress. **Observation unavailable**,
  **Event age unavailable**, or **Observation time unavailable** means the
  corresponding evidence is missing, stale, or unusable. Do not read it as zero lag.

Follow **Maintained by** to inspect the pipeline. Compare a known source change
with the destination before concluding that delivery is current or correct.
See [View observation fields](/docs/reference/rest-api#view-observation-fields)
for the API representation.

## Check data correctness

Monitoring explains runtime activity. To compare stable source and destination
data for a direct one-to-one pipeline, follow
[Validate pipeline data](/docs/guides/validate-pipeline-data). For Nest or other
transforms, compare the expected output documents and representative changes,
as shown in [Build a pipeline](/docs/guides/build-a-pipeline#5-check-the-result).

## Follow an alert

Open **Alerts** in the Cluster sidebar to inspect active problems and recovery
evidence. Use **Alert diagnostics** to check detection and notification-system
status. Notification delivery is tracked separately from the fault itself.
See [Alerts and notifications](/docs/manage/alerts) for rules, maintenance
silences, and Cloud delivery.

## Build an evidence set

For a run review, capture:

- organization, Cluster name, **Runtime version** from **Clusters**, and
  pipeline ID;
- current sync health, **Monitoring** figures, and per-table progress;
- relevant **Logs** lines and failure codes;
- source and target row counts, plus insert, update, and delete samples;
- timestamps and the expected result.

Remove secrets and customer data before sharing the evidence.
