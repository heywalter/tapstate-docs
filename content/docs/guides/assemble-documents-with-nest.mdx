Use `nest` when an application needs one current document but the source stores
that entity across related tables. The transform builds the document during the
initial load and updates it as MySQL emits later changes.

This guide uses an `orders` root table and an `order_items` child table. It
assumes the v0.2 playground or another non-production server is running, the
MySQL and MongoDB connector artifacts are registered, and both connections pass
a server-side test.

## 1. Choose the document root

Start with the entity that should produce one output document. In this example,
each `orders.id` becomes one MongoDB document. Every item carries the parent
identity in `order_items.order_id`:

```text
orders.id  1 ─────< order_items.order_id  1
```

`nest` follows parent identity. It is not a general lookup or SQL join. If a
child row does not carry the key that points to its parent, redesign the source
shape or choose a different document root.

## 2. Select the source tables

Use one CDC-capable MySQL connection and select both tables:

```yaml title="tapstate-work/source/orders_source.tap.yml"
version: tapstate/v1
kind: source
id: orders_source
connector: mysql
config:
  host: db.internal
  port: "3306"
  database: shop
  username: ${MYSQL_USER}
  password: ${MYSQL_PASSWORD}
mode: cdc
tables: [orders, order_items]
```

The MongoDB connection is the materialization target, so it has no `mode` or
`tables`:

```yaml title="tapstate-work/source/operational_state.tap.yml"
version: tapstate/v1
kind: source
id: operational_state
connector: mongodb
config:
  isUri: true
  uri: "mongodb://${MONGO_USER}:${MONGO_PASSWORD}@mongo.internal:27017/shop?authSource=admin"
```

Keep credentials out of committed files. See the [MySQL](/docs/connectors/mysql)
and [MongoDB](/docs/connectors/mongodb) guides for permissions and connection
fields.

## 3. Define the document tree

Map short aliases to the source table streams, choose the root key, and describe
where each child belongs:

```yaml title="tapstate-work/pipeline/order_documents.tap.yml"
version: tapstate/v1
kind: pipeline
id: order_documents
source: orders_source
settings:
  read_mode: snapshot_and_cdc
transforms:
  - id: document
    type: nest
    from:
      order: orders
      item: order_items
    root:
      from: order
      key: [id]
      embed:
        - from: item
          on:
            order_id: id
          as: array
          path: items
          arrayKey: [id]
          trackKeyChanges: true
serve:
  from: document
  sync:
    - id: write_documents
      source: operational_state
      write_mode: upsert
      ddl: fail
```

Here, `on` means `order_items.order_id` must equal `orders.id`. `as: array`
creates `items: []` when an order has no children. Use `as: object` only when
the relationship has at most one child.

`trackKeyChanges: true` moves an embedded row when its item key or parent key
changes. It requires the source connector to provide a before image. Leave it
off when those keys are immutable.

## 4. Discover schemas, then apply again

Validate locally, apply the connections, discover both source schemas, and
apply the pipeline again before starting it:

```text
tapstate validate --workdir tapstate-work
tapstate -w tapstate-work
connect http://127.0.0.1:8080
login admin
apply
discover-schema orders_source
apply
start order_documents
status order_documents
```

Discovery lets tapstate estimate the capacity required by each nest level. An
apply before discovery can report `nest.capacity-estimate-incomplete`; it is a
floor estimate, not proof that the pipeline has enough capacity.

## 5. Verify initial state and CDC

Do not treat an accepted `start` command as proof that data moved. Verify all of
the following:

1. `status order_documents` remains `running`.
2. `logs order_documents` has no unresolved coded failure.
3. `metrics order_documents` shows processed records and no unexplained
   `dead_lettered` changes.
4. MongoDB contains one document per order and the expected number of embedded
   items.
5. A representative item insert, update, parent-key change, and delete produces
   the expected whole document in MongoDB.

A nest emits and writes the assembled document as a unit. Include a document
near the expected maximum size in capacity and latency tests; a backing state
layer cannot make one oversized document fit.

## Current limits

- Every nested relationship must point from child to parent.
- Sibling branches at the same level must agree on the parent identity.
- `nest` does not perform arbitrary lookups; the separately declared `join`
  transform remains refused by the current runtime.
- Key-change tracking depends on complete before images.
- The v0.2 runtime is single-node and does not provide production recovery
  guarantees.
