Use `nest` when an application needs one current document from related tables,
including tables in different database engines. The transform builds each
document during the initial load and updates it whenever either source commits
a change.

For the visual Cloud workflow using **Pipeline builder** (**Array**,
**Document**, and **Flatten**), follow
[Build a pipeline](/docs/guides/build-a-pipeline). Use this guide when authoring
`.tap.yml` workspace files and applying them with the `tapstate` CLI on a local
workspace or self-hosted server. Cloud Clusters authenticate with browser
sessions and do not accept CLI bearer tokens; see
[CLI scope](/docs/self-hosted#cli-and-automation).

## 1. Choose the document root

Start with the entity that should produce one output document. In this example,
each `orders.id` becomes one materialized document, and every shipment row
carries its parent key in `shipments.order_id`:

```text
orders.id  1 ─────< shipments.order_id  1
```

`nest` follows parent identity. It is not a general lookup or SQL join. If a
child row does not carry the key that points to its parent, redesign the source
shape or choose a different root.

For mutable parent, root, or array keys on a self-hosted pipeline, configure
[structural key tracking](/docs/guides/nest-structural-key-changes) when source
before images are available.

## 2. Declare both sources in `.tap.yml`

Prepare both source databases using the [MySQL](/docs/connectors/mysql) and
[PostgreSQL](/docs/connectors/postgresql) guides (for a PostgreSQL child table
that can be updated or deleted, set `REPLICA IDENTITY FULL` before starting
CDC).

Create one CDC-capable source file for each database engine, keeping secrets in
environment variables:

```yaml title="tapstate-work/source/orders_db.tap.yml"
version: tapstate/v1
kind: source
id: orders_db
connector: mysql
config:
  host: mysql.internal
  port: 3306
  database: shop
  username: ${MYSQL_USER}
  password: ${MYSQL_PASSWORD}
mode: cdc
tables: [orders]
```

The PostgreSQL source uses its own field names and selects the shipment table:

```yaml title="tapstate-work/source/fulfillment_db.tap.yml"
version: tapstate/v1
kind: source
id: fulfillment_db
connector: postgres
config:
  host: postgres.internal
  port: 5432
  database: fulfillment
  schema: public
  user: ${POSTGRES_READER_USER}
  password: ${POSTGRES_READER_PASSWORD}
  logPluginName: pgoutput
mode: cdc
tables: [shipments]
```

## 3. Define the `nest` pipeline and `view`

Define the pipeline, mapping short aliases to the source table streams, choosing
the root key, and describing where each child belongs:

```yaml title="tapstate-work/pipeline/order_pipeline.tap.yml"
version: tapstate/v1
kind: pipeline
id: order_pipeline
source: [orders_db, fulfillment_db]
settings:
  read_mode: snapshot_and_cdc
transforms:
  - id: assemble
    type: nest
    from:
      order: orders
      shipment: shipments
    root:
      from: order
      key: [id]
      embed:
        - from: shipment
          on:
            order_id: id
          as: array
          path: shipments
          arrayKey: [id]
view:
  id: order_state
  from: assemble
  primary_key: id
```

Here, `on` means `shipments.order_id` must equal `orders.id`. `as: array`
creates `shipments: []` when an order has no children. Use `as: object` when
the relationship has at most one child, or an
[`as: flat` embed](/docs/reference/transforms#flat-embeds) when one related
row's fields should sit directly on the parent. On v0.8, optional
`state.database` selects a separate cache database at creation time; moving an
existing Nest's state ([Move Nest state](/docs/guides/move-nest-state)) applies
only to legacy v0.7 single-store deployments. For larger trees, you can also
set optional `entries_in_memory` (deployment default `4,000`, minimum `271`,
consistent across all `nest` steps in a pipeline) and `max_elements_per_document`
(deployment default `20,000`) bounds; see
[Plan nest capacity and delivery behavior](/docs/guides/nest-throughput).

## 4. Validate, discover, apply, and verify

Validate locally, apply each source to your self-hosted server, discover its
schema, apply the complete workspace, and start the pipeline:

```text
tapstate validate --workdir tapstate-work
tapstate -w tapstate-work
connect http://127.0.0.1:8080
login admin
apply source/orders_db.tap.yml
apply source/fulfillment_db.tap.yml
discover-schema orders_db
discover-schema fulfillment_db
apply
start order_pipeline
status order_pipeline
```

The first two `apply` commands store the connections before discovery. The final
`apply` stores the pipeline after discovery has supplied both sources' field
types. Verify the run and assembled output before treating delivery as healthy:

1. Check `status order_pipeline`, `logs order_pipeline`, and
   `metrics order_pipeline` (including any `nestDeadLettered.<namespace>` counts;
   see [Observe self-hosted pipelines](/docs/self-hosted/observe-pipelines)).
2. Check the materialized `order_state` view for one document per order with
   embedded `shipments`.
3. Test a PostgreSQL shipment insert, update, and delete alongside a MySQL
   order update, confirming the expected document updates in place.

A `nest` writes the assembled document as a unit. Include a document near the
expected maximum size in capacity and latency tests—see
[Plan nest capacity and delivery behavior](/docs/guides/nest-throughput).

## Current limits

- Every nested relationship must point from child to parent.
- Sibling branches at the same level must agree on the parent identity.
- `nest` does not perform arbitrary lookups; use the separately declared
  [`join` transform](/docs/reference/transforms#join) for stream-to-stream
  joins between a driving fact table and dimension sources.
- Self-hosted servers default to one member with opt-in
  [cluster mode](/docs/guides/cluster). The preview does not provide production
  recovery guarantees.

Continue with the [`nest` reference](/docs/reference/transforms#nest) for every
YAML field, [Handle structural key changes with nest](/docs/guides/nest-structural-key-changes),
and [Plan nest capacity and delivery behavior](/docs/guides/nest-throughput).
