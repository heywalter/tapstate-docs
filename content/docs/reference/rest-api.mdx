The preview server exposes an HTTP control plane. This API exists only
after a separate tapstate server is running; installing the CLI does not start
the server or expose an HTTP port. The server image includes the web
application at the server's root URL.

The API has no stable OpenAPI publication or versioned URL namespace yet; pin
the tapstate release and treat request and response compatibility as
prerelease.

Use the web application for interactive work. This page documents the Cluster
control-plane API (`/api/**` and `/auth/**` on a Cluster or self-hosted server).
Cloud organization, subscription, and Cluster-provisioning actions on
`https://cloud.tapstate.com` use a separate `/v1/api/**` service (such as
stabilizing a Cluster's outbound address) and are not part of the Cluster
runtime contract below.

Several Cluster endpoints below—including three-layer storage operations, data
validation, alert management, start checks, and whole-pipeline deletion—serve
Cloud and v0.8 self-hosted runtimes and are unavailable in v0.7 self-hosted
builds. Check the deployment notes in each section rather than assuming a v0.7
server exposes every route. Use REST for integrations that handle
authentication, coded errors, and contract changes.

## Base URLs and authentication

Public endpoints and sign-in endpoints:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/healthz` | Process/engine liveness: `200 ok`, or `503 broken` after engine loss. |
| `GET` | `/version` | Report the server release and its versioned contracts. |
| `GET` | `/.well-known/tapstate` | Read issuer, cluster identity, API version, and self-hosted authentication modes before presenting a cached credential. In Cloud, authenticate with the managed browser session rather than selecting a mode from `supportedAuthModes`. |
| `GET` | `/connector-icons/{id}` | Read icon bytes for a registered connector; returns 404 if unavailable. |
| `POST` | `/auth/bootstrap` | First-administrator bootstrap from loopback for the v0.7 self-hosted layout; v0.8 three-layer installations use `/installation/first-admin` on the dedicated management channel. |
| `POST` | `/auth/login` | Exchange username/password for a short-lived bearer token; it can also create a revocable user session. |

### Read the server version

`GET /version` is available before authentication so a client can identify the
server before it logs in or reasons about supported operations:

```bash
curl -sS http://127.0.0.1:8080/version
```

```json
{
  "version": "0.8.0",
  "dslVersions": ["tapstate/v1"],
  "dataVersion": 3
}
```

`version` identifies the server release. `dslVersions` lists the accepted
authoring grammars, and `dataVersion` identifies the control-store schema.
The example shows a v0.8.0 three-layer Configuration store (v0.7 single-store
deployments report `dataVersion: 12`). Use the reported values
when checking an upgrade; installing a newer CLI does not change them.

Use `/healthz` for process/engine liveness. An engine lost to out-of-memory
returns `503` with `broken`. A `200` response does not verify source, target, or
MongoDB health and does not identify the running build.

On a self-hosted server, authenticate `/api/**` requests with:

```http
Authorization: Bearer <token>
```

See [Bootstrap and authenticate](/docs/guides/bootstrap-and-auth) for the request sequence.

Cloud Cluster workspaces authenticate `/api/**` requests with the
`__Host-tapstate-cloud-session` cookie established by `/auth/exchange` instead
of bearer tokens or local users. Sending an `Authorization` header to a Cloud
Cluster is refused with HTTP `401`. For state-changing methods (`POST`, `PUT`,
`PATCH`, `DELETE`), cookie-authenticated requests must pass same-origin checks:
if an `Origin` header is present, a single matching origin is required; when
`Origin` is absent, `Sec-Fetch-Site` must be absent, `same-origin`, or `none`.
Endpoint availability depends on the deployment mode.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/auth/me` | Read the authenticated identity; the response is not cacheable. |
| `GET` | `/api/cluster/context` | Read Cloud session identity and current cluster network context; Cloud only. |

`GET /api/auth/me` returns `mode`, `principal`, `scopes`, `username`, and
`email`. Cloud reports `username: null` and an email only when the managed
session supplies one. Self-hosted accounts report their username; `email` is
that username only when it has an email-address form, otherwise `null`.
Neither nullable field is a stable identity key or proof of email verification.

Cloud sign-in also exposes these system routes:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/auth/exchange` | Exchange a provider-issued `code`, set the Cloud session cookie, and redirect to `/`. |
| `POST` | `/auth/invalidate-session` | Provider back-channel callback to invalidate a Cloud session. |

The invalidation callback requires `jti`, `ts`, `nonce`, and `sign` parameters
verified against the provider's signature over `POST|ts|nonce|jti`. A user
bearer token does not authorize this callback. Both routes are Cloud-only and
return non-cacheable responses.

### Create and use a user session

These endpoints manage local user sessions on a self-hosted server, and
`/auth/logout` also clears the Cloud session cookie when called on a Cloud
Cluster.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/auth/session` | Exchange a saved self-hosted user session for a fresh bearer token. |
| `POST` | `/auth/logout` | Revoke a saved self-hosted session (`TapstateSession` header) or clear the Cloud session cookie. |

`POST /auth/login` remains compatible with callers that send only `username`
and `password`: its `token` is the short-lived bearer credential for `/api/**`.
Set `createSession` to `true` only when the client needs a revocable user
session that it can later exchange for fresh bearer credentials:

```json
{
  "username": "admin",
  "password": "<password>",
  "createSession": true
}
```

When requested, the response also includes `sessionToken`,
`sessionIdleExpiresAt`, and `sessionAbsoluteExpiresAt`. Keep the session token
secret. It is not a `Bearer` token and must not be sent to `/api/**`.

To obtain a fresh access token, send the session token to `POST /auth/session`:

```http
Authorization: TapstateSession <sessionToken>
```

The response has the ordinary access-token fields (`token`, `accessExpiresAt`,
`issuer`, `principal`, and `scopes`); use its `token` as the `Bearer` value for
`/api/**`. Send the same `TapstateSession` header to `POST /auth/logout` to
revoke a self-hosted session. On a Cloud Cluster without an `Authorization`
header, `POST /auth/logout` clears the `__Host-tapstate-cloud-session` cookie
and returns HTTP `204`.

### Self-hosted browser sessions

Starting with v0.8, the bundled web application uses these same-origin endpoints
for local accounts. They are separate from the CLI user-session endpoints and
are unavailable in Cloud mode.

| Method | Path | Result |
|---|---|---|
| `POST` | `/auth/browser/login` | Accept JSON `username` and `password`; set an HttpOnly session cookie (`__Host-tapstate-op-session` over HTTPS or `tapstate-op-session` on allowed loopback) and return an access-token grant. |
| `POST` | `/auth/browser/session` | Exchange the browser cookie for a fresh access-token grant. |
| `POST` | `/auth/browser/logout` | Revoke the browser session, clear its cookie, and return `204`. |

Each request must include `X-Tapstate-Browser-Request: 1` and a single `Origin`
matching the request's public scheme, hostname, and port. Do not send an
`Authorization` header to these browser endpoints. HTTPS origins must be
explicitly allowed; plain HTTP is refused by default. Follow
[Configure self-hosted browser access](/docs/guides/bootstrap-and-auth#configure-self-hosted-browser-access)
for the allowed-origin, trusted-proxy, and loopback settings.

The browser manages the cookie; the response does not expose its session
credential to JavaScript. Keep the returned access token in memory and send it
as `Authorization: Bearer <token>` on ordinary `/api/**` calls. Authentication
responses use `Cache-Control: no-store`. Logout prevents further session
exchanges but does not immediately invalidate access tokens already issued.

### Cloud cluster network context

`GET /api/cluster/context` requires the managed Cloud session. It returns the
organization and Cluster identity together with these network fields:

| Field | Meaning |
|---|---|
| `ec2PublicIp` | Current outbound IPv4 address reported by Cloud, or `null` when unavailable. Use the returned value for database allowlisting. |
| `egressAddressStatus` | Address lifecycle and stability status reported by Cloud, or `null` when unavailable. This is separate from the Cluster's runtime health. |
| `clusterState` | `null` in this response; do not infer that the Cluster is Ready from it. |
| `userEmail` | Email supplied by the authenticated Cloud session, or `null` when unavailable. |

Interpret `egressAddressStatus` as follows:

| Value | Meaning and next action |
|---|---|
| `DYNAMIC` | An instance-assigned address, used by older Clusters; it may change when the instance is replaced. Recheck the address after replacement. |
| `STABILIZING` | A stable address is being attached to the Cluster. Wait for the transition to finish before finalizing allowlists. |
| `ATTACHING` | Address association or Cluster provisioning is in progress. Check again when the Cluster is ready. |
| `STABLE` | A Cluster-owned Elastic IP is associated with the current node. Use the reported address; this status does not verify database connectivity. |
| `FAILED` | A stable address could not be established, or the Cluster is not in a state that can report a live address. Check Cluster status and contact support if the condition persists. |

The address is refreshed from Cloud rather than frozen at sign-in. Reads use a
short-lived cache: the default refresh interval is 30 seconds, and a cached
address can be retained for up to five minutes during provider failures.
Responses use `Cache-Control: no-store` for HTTP clients. A missing address is
not permission to allow all source addresses, and a returned address does not
prove database connectivity. Treat unknown address-status values as unknown;
do not use this field as a pipeline readiness check.

## Artifact endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/artifacts:apply` | Parse, validate, and apply a batch of raw YAML drafts. |
| `POST` | `/api/artifacts:validate` | Parse and validate a batch of raw YAML drafts without storing them. |
| `GET` | `/api/artifacts` | List stored artifacts; optional `kind` query parameter. |
| `GET` | `/api/artifacts/{id}` | Read one stored artifact. |
| `DELETE` | `/api/artifacts/{id}` | Permanently remove one stored artifact; requires `If-Match` with the current content hash. |

Artifact deletion requires a quoted 64-character content hash from the artifact's current representation:

```http
If-Match: "<64-hex-content-hash>"
```

Read the artifact first to obtain the hash. The `contentHash` field is the
unquoted 64-character value returned by `GET /api/artifacts/{id}` (and by the
artifact list); wrap that value in quotes only when forming the `If-Match`
header:

```json
{
  "id": "orders_source",
  "kind": "source",
  "canonicalForm": "...",
  "contentHash": "<64-hex-content-hash>"
}
```

The server returns `428` when the header is missing or malformed, `412` when the hash is stale, and `204` after the artifact is removed.

Source artifacts have a display-only `canonicalForm`: connector `config` is
omitted, while `contentHash` still identifies the full stored resource. Do not
use this output as a backup or reapply it as a complete Source definition.
Use the structured Source endpoints to edit an existing connection.

Apply request:

```json
{
  "drafts": [
    {
      "source": "source/orders_source.tap.yml",
      "content": "version: tapstate/v1\nkind: source\nid: orders_source\nconnector: mysql\nconfig:\n  host: mysql.invalid\n  port: \"3306\"\n  database: appdb\n  username: tapstate\nmode: snapshot\n"
    }
  ]
}
```

The server reparses the YAML and returns one `CREATED`, `UPDATED`, or `UNCHANGED` outcome per draft.

The drafts are validated together as a workspace. Include the resources they
reference in the same batch; a Source already stored on the server does not
satisfy a missing reference in an otherwise incomplete draft workspace.

The validate endpoint returns a validation report. HTTP `200` can contain
`valid: false` and entries in `diagnostics`; check `valid` before treating the
workspace as accepted. For example, a v0.6 View that still includes `schema`
reports `dsl.unknown-field` in that list.

Apply can return `dsl.upsert-needs-key` after source discovery. Its `params`
identify the affected `source`, `table`, and resource `path`. Select a source
table with a discovered primary key, or use `append` only for insert-only
delivery. A unique index, target-side key, or `tables[].pk` does not satisfy the
current runtime check.

### Preview pipeline data

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/artifacts:preview` | Execute a bounded, no-write sample preview and stream NDJSON events. |

The request contains `pipelineId` and a `drafts` array in the apply-request
shape. Optional fields are `outputId`, `rootLimit`, and `sampleId`. A draft
can include `expectedContentHash` to guard against a changed stored resource.
The request is limited to 256 drafts and 4 MiB.

Send `Accept: application/x-ndjson, application/json` to accept both the event
stream and JSON errors returned before streaming starts.
The successful response content type is `application/x-ndjson`. Read each event's `kind`
and `payload`; HTTP `200` means the stream opened, not that the preview
succeeded. `run.completed` and `run.failed` are terminal events. Closing the
connection cancels the preview.

Preview has a 45-second deadline and uses a default and maximum `rootLimit`
of 100 root samples. It neither applies the candidate resources nor writes to
the target. Results can use `mongo-extended-json` when the MongoDB target's
codec can render them, or `logical-json` otherwise; inspect the result format.
Sampling does not verify continuous CDC delivery. For draft compilation
without sample reads, use `draft:preview` below.

## Connector and connection endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/connectors:register` | Register a base64-encoded connector JAR. |
| `GET` | `/api/connectors` | List the bundled and registered online catalog. |
| `GET` | `/api/connectors/{id}/icon` | Read the registered connector icon, or 404 if unavailable. |
| `GET` | `/api/connectors/{id}` | Read one connector's normalized fields and capabilities. |
| `POST` | `/api/connections:test` | Run and store a connector connection test synchronously. |
| `GET` | `/api/connections/{id}/test-result` | Read the latest stored test report. |
| `POST` | `/api/connections:discover-schema` | Run and store source discovery synchronously. |
| `GET` | `/api/connections/{id}/schema` | Read the latest stored discovered model. |

Use `tapstate register` instead of manually base64-encoding large JARs when possible.

Connection test request:

```json
{
  "id": "orders_source",
  "connectorId": "mysql",
  "settings": {
    "deploymentMode": "standalone",
    "host": "mysql.invalid",
    "port": "3306",
    "database": "appdb",
    "username": "tapstate"
  }
}
```

A connector that completes its checks normally returns HTTP `200` even when the report has `outcome: "FAILED"`. Inspect the outcome and checks. A connector that throws during testing returns a coded error response instead.

Connection test and discovery execute synchronously and can take longer than ordinary reads. Configure the caller and any reverse proxy with an appropriate timeout, and do not retry a write blindly.

The CLI and MCP gateway wait for connection tests and discovery without a
fixed request deadline. A timeout imposed by another caller or proxy does not
prove that the server stopped the operation; read its stored result before
retrying.

## Source endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/sources:draft` | Validate a structured Source draft and render canonical YAML without storing it. |
| `POST` | `/api/sources` | Create one structured source. |
| `GET` | `/api/sources` | List structured sources. |
| `GET` | `/api/sources/{id}` | Read a secret-redacted source and its `ETag`. |
| `PUT` | `/api/sources/{id}` | Replace a source using `If-Match`. |
| `DELETE` | `/api/sources/{id}` | Delete a source using `If-Match`. |
| `GET` | `/api/sources/{id}/schema` | Read the discovered schema scoped specifically to the source's selected tables. |

`GET /api/sources/{id}/schema` filters the discovered schema to only the tables declared in the source's `tables` configuration. To inspect the full catalog of all discovered tables across the database, use `GET /api/connections/{id}/schema`.

When running `POST /api/connections:test` or `POST /api/connections:discover-schema` for an existing stored source, omitting secret fields (such as `password`) automatically reuses the credentials saved on the server.

`POST /api/sources:draft` is an authoring check, not a create operation. It
returns a redacted Source view and canonical YAML only when the live connector
catalog can supply the complete connector contract; it creates no artifact or
audit record.

Update and delete require the quoted 64-character content hash returned in `ETag`. Missing or stale preconditions return HTTP `428` or `412`. Secret values are not returned; use the structured secret-clearing contract deliberately when replacing a source.

### Edit saved credentials

The following preservation and clearing rules describe the Cloud
structured Source endpoints.

For a structured update that keeps the same connector, omit a saved secret to
retain it, supply a new value to replace it, or name it in `clearSecrets` to
remove it. This includes catalog secrets and shared transport paths `sslKey`,
`sslKeyPassword`, and the configured SSH password path. A supplied null is rejected; do
not use null as a clearing operation. Supplying and clearing the same path in
one request is also rejected.

Responses expose `configuredSecrets` names rather than secret values. A
connection test for that same saved Source and connector restores omitted
credentials. Changing the connector does not inherit the old connector's
credentials. Connection-test diagnostics preserve their useful messages and
codes while redacting configured secret values.

These rules do not create TLS/SSH options for a connector that does not expose
them. See [Source configuration](/docs/reference/source#config) for the resource
format and keep complete credentials in your own secure backup.

Use one write model consistently. Prefer `/api/artifacts:apply` for resource
authoring and pipeline batches. Use the structured source endpoints when a
client needs source-specific draft and `ETag` workflows.

## Data validation

These `/api/validation:*` and `/api/pipelines/{pipeline}/validation-tasks/**`
endpoints serve Cloud and v0.8 self-hosted runtimes and are unavailable in v0.7
self-hosted builds. For the Web workflow, see
[Validate pipeline data](/docs/guides/validate-pipeline-data).

Validation tasks are separate from pipeline execution and alert detection.
Their conclusions apply to the records read during validation. They do not
establish a common-time snapshot across databases. Finish initial synchronization
and keep both sides stable before using the comparison to assess consistency.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/validation:evaluate` | Evaluate proposed task mappings and comparison keys before saving. |
| `POST` | `/api/validation:save` | Save the evaluated task with its fingerprint and expected revision. |
| `GET` | `/api/pipelines/{pipeline}/validation-tasks/{task}` | Read the saved task, current revision, and execution context. |
| `POST` | `/api/validation:schedule-preview` | Preview occurrences for a schedule and input revision. |
| `POST` | `/api/validation:schedule-disable` | Disable a saved schedule with its current task identity and revision. |
| `POST` | `/api/validation:start` | Request a validation run using the original task and execution context. |
| `POST` | `/api/validation:progress` | Read the original validation operation. |
| `POST` | `/api/validation:stop` | Request that the original validation operation stop. |
| `GET` | `/api/pipelines/{pipeline}/validation-tasks/{task}/reports` | List retained reports for a task. |
| `GET` | `/api/pipelines/{pipeline}/validation-tasks/{task}/reports/{run}` | Read one report by its original generation, sequence, and run. |
| `GET` | `/api/pipelines/{pipeline}/validation-tasks/{task}/reports/{run}/roots` | List root-level findings for the selected report. |
| `GET` | `/api/pipelines/{pipeline}/validation-tasks/{task}/reports/{run}/roots/{root}` | Read one root-level finding from that report. |

Evaluate, save, start, stop, and schedule-disable require write scope. Task,
progress, and report reads and schedule-preview require read scope. POST bodies
are JSON, limited to 256 KiB; unknown properties and invalid field types are
rejected. Responses use `Cache-Control: no-store`.

Evaluation takes `pipelineId`, `taskId`, `taskGeneration`, `expectedRevision`,
`method`, `mappings`, and `confirmations`. A save wraps that input with its
returned `fingerprint`, a `commandId`, `historyLimit`, `schedule`, and
`scheduleEnabled`. Reevaluate changed definitions rather than reusing a stale
fingerprint. Save and schedule-disable return `200` for `APPLIED` or `DUPLICATE`
and `409` for other write outcomes.

Start, progress, and stop share `context`, `pipeline`, `task`, `taskGeneration`,
`revision`, `sequence`, and `command`. Read the current task before starting;
retain the response's `original` object for subsequent progress and stop
requests. A pending or unknown result must be checked as the original operation
before another start. Starting or stopping validation does not start or stop
the pipeline itself.

Report history uses `offset` (default 0, maximum 4096) and `limit` (default 10,
maximum 20). A report, its roots, and a specific root require the original
`generation` and `sequence` query parameters in addition to the run in the
path. Use the reference returned by report history. Do not combine a run with
the current task generation after the task has been replaced. Root lists use
the same paging bounds. A missing report returns `404`.

## Alerts and notifications

These `/api/alerts/**` endpoints inspect and manage alerts on Cloud and v0.8
self-hosted deployments; they are unavailable in v0.7 self-hosted builds. Every
request is a JSON object, including reads with `{}`. Responses use
`Cache-Control: no-store`; request bodies are limited to 64 KiB. The server
establishes Cluster scope from the authenticated session.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/alerts/catalog` | Read available alert types, parameter ranges, connected inputs, and deployment channels. |
| `POST` | `/api/alerts/resources` | List current resource identities for configuration. |
| `POST` | `/api/alerts/center` | List active alerts or ended episodes. |
| `POST` | `/api/alerts/detail` | Read an alert episode, evidence, and retained diagnostics. |
| `POST` | `/api/alerts/deliveries` | List notification attempts or read one delivery. |
| `POST` | `/api/alerts/health` | Read detector and notification-system health. |
| `POST` | `/api/alerts/configuration/list` | List active configuration records of one kind. |
| `POST` | `/api/alerts/configuration/save` | Create or update a rule, route, receiver, or silence. |
| `POST` | `/api/alerts/configuration/retire` | Retire an existing configuration record. |
| `POST` | `/api/alerts/rule-preview` | Evaluate a synthetic rule example without saving or publishing an alert. |
| `POST` | `/api/alerts/route-preview` | Preview current alerts matching a proposed notification route; self-hosted only. |
| `POST` | `/api/alerts/preview` | Render example notification content without sending it; self-hosted only. |
| `POST` | `/api/alerts/test` | Send a fixed test message using the current receiver candidate; self-hosted only. |
| `POST` | `/api/alerts/test-result` | Query the original receiver test by `commandId`; self-hosted only. |
| `POST` | `/api/alerts/retry` | Authorize another bounded delivery cycle; self-hosted only. |

### Read alert state

Use `catalog` before building a configuration client. It reports type IDs,
versions, supported resource kinds, parameter defaults and bounds, and whether
the relevant input is connected. An available type does not prove that its
input is currently healthy.

For example, send this body to `/api/alerts/center`:

```json
{"view": "active", "limit": 25}
```

`view` is `active` (the default) or `history`. Optional filters are `severity`,
`search`, and `endReason`; history defaults to `endReason: "RECOVERED"`.
History can also end because a rule was disabled, replaced, or its resource
removed. Those outcomes do not establish recovery.

Paged reads use `limit` (default 25, maximum 100) and `cursor`; follow
`nextCursor` until it is absent. Keep the same filters when continuing a page.
Use the returned opaque `key` and `episode` for `/api/alerts/detail`.
`/api/alerts/deliveries` accepts an `id` for one delivery, or paging and optional
`channel`, `result`, `key`, and `episode` filters. Inspect `isolated` when
present: unsupported retained records can make coverage incomplete.

Catalog, center, detail, delivery, and health reads require read scope.
Configuration and resource reads and rule examples require write scope in
Cloud and administrator access on self-hosted servers. Self-hosted notification
tests, test-result reads, content previews, route previews, and delivery retries
also require administrator access. Deployment restrictions still apply even with
elevated access.

### Save configuration and inspect sends

Configuration requests use `kind`: `RULE`, `SILENCE`, `SUBSCRIPTION`, or
`RECEIVER`. Save with `kind`, `id`, `etag`, and `form`; use `etag: "0"` for a
new record and the returned revision for updates. Retire an existing record
with `kind`, `id`, and its current `etag`. The revision is a JSON field, not an
HTTP `If-Match` header. Reload and review conflicts before retrying.

Rules and silences are available in both Cloud and v0.8 self-hosted
deployments. `SUBSCRIPTION` and `RECEIVER` configuration is self-hosted only;
Cloud sends through its managed event service and organization policy. Do not
infer that an accepted Cloud event has reached a recipient. Direct local
notification sending is unavailable in Cloud-managed Clusters.

Self-hosted receiver tests accept a caller-generated `commandId`, a
`candidateId`, and the current `form` (plus `existingId` and `etag` when testing
a saved receiver, and `target` for one Email recipient). Query
`/api/alerts/test-result` with that same `commandId` if a test times out; an
unknown result is not permission to resend automatically. Delivery retries accept
the delivery's `id` and current `etag`, keep the original target, content, and
deadline, and can duplicate a message when the earlier outcome is unknown.

For the configuration fields and interactive sequence, use
[Alerts and notifications](/docs/manage/alerts).

## Storage and configuration operations

`GET /auth/storage-entry` returns anonymous navigation hints in both Cloud and
self-hosted deployments without granting storage access. The `/api/storage/**`
and `/api/configuration/**` endpoints in this section serve the three-layer
runtime on Cloud and v0.8 self-hosted servers and are unavailable in v0.7
self-hosted builds. They do not migrate an older metadata layout or rebind a
running installation to different databases. For the interactive procedures, see
[Cluster storage setup](/docs/quickstart#2-connect-storage) and
[self-hosted storage initialization](/docs/guides/bootstrap-and-auth#initialize-storage).

| Method | Path | Purpose |

| `POST` | `/api/storage/status` | Read setup, health, and permitted actions; send `{}`. |
| `POST` | `/api/storage/test` | Test the proposed CACHE connection and return a time-limited test stamp. |
| `POST` | `/api/storage/setup/commit` | Save the tested binding and continue initialization. |
| `POST` | `/api/storage/setup/status` | Read the original setup operation by `operationId`. |
| `POST` | `/api/storage/setup/activate` | Continue activation of the original saved binding when allowed. |
| `POST` | `/api/storage/recovery/plan` | Preview the affected scope before recovery. |
| `POST` | `/api/storage/recovery/confirm` | Confirm the exact recovery plan and revision. |
| `POST` | `/api/storage/recovery/status` | Read the original recovery operation by `operationId`. |
| `POST` | `/api/configuration/export` | Export selected configuration as an encrypted transfer package. |
| `POST` | `/api/configuration/import/preflight` | Check an import and return its operation and prepared transfer. |
| `POST` | `/api/configuration/import/commit` | Commit the checked import without overwriting existing resources. |
| `POST` | `/api/configuration/import/status` | Read the original import by `importId`. |

All POST requests require a JSON object, including status reads. Responses use
`Cache-Control: no-store`. Authentication, setup purpose, and the original
Cluster scope determine which operations are allowed. A session or request
body cannot choose another Cluster's storage scope. Self-hosted initial setup
uses the dedicated management channel; an ordinary bearer token does not replace
installation authorization.

`POST /installation/first-admin` accepts only `username` and `password` in its
JSON body on the dedicated management channel and returns HTTP `200` with
`{"phase": "COMPLETE", "next": "login"}`. The ordinary server listener rejects
it with `control.bootstrap-forbidden`.

### Test and save storage

Read storage status first. Retain its `operationId` and `setupGeneration`; send
the latter as `generation` in test and commit requests. In Cloud, `candidate`
contains `cache` and `master` while Configuration comes from the deployment; on
v0.8 self-hosted installations, `candidate` contains `configuration`, `cache`,
and `master`.

Each connection contains `kind` (`MONGODB` or `ATLAS`), `uri`, and `database`.
An optional `caPem` supplies a supported custom CA bundle, up to 64 KiB.
`master` is the API name for Application data. Do not use a custom-CA-only
application target; that connector path is outside storage setup's TLS support.

A test request contains `operationId`, `generation`, `candidate`, and
`layer: "CACHE"`. Initial setup rejects tests for `CONFIG` or `MASTER`. The
response includes `testStamp`, `expiresAt`, and the checks performed.
For a new binding, the Cache check also requires an empty database: any existing
collection, even with zero documents, is refused. Collection-listing permission
is required. An occupied-database diagnostic can include a checked empty name
suggestion; a client must test the selected candidate again. Occupancy is
rechecked before the first binding is saved. Keep the original Cache database
when continuing an existing binding.

Commit with `operationId`, `generation`, the complete `candidate`, and
`testStamps: {"CACHE": "<returned-test-stamp>"}`. The stamp map must contain
only `CACHE`. The server validates Configuration and Durable cache before
binding them; Application data is checked separately after activation.

Changing the cache connection or letting its test expire requires a new test.
Changing only Application data does not invalidate the cache stamp, but the
complete candidate must still pass validation, including distinct database
names. Never reuse a stamp for a different operation or generation.

A successful save is separate from runtime readiness. Check `businessPhase`,
individual layer `health`, and `initializationProgress` when present. If a
response is lost, query the original operation before retrying. First Cloud
activation preserves unexpired sessions and revocation state in the original
Cache; another sign-in exchange is not normally required. If a request crosses
the authentication transition and fails, re-enter the same Cluster through
Cloud and check the original operation.

### Continue saved activation

If status offers `storage.setup.activate`, send the original `operationId`,
`generation` (the current `setupGeneration`), and `bindingVersion` to
`POST /api/storage/setup/activate`. Do not include a new candidate or test
stamps. The operation continues the saved binding; it does not edit the
default Source or reinitialize storage. Query status after the request and
check runtime readiness separately from `setupPhase: "COMPLETE"`.

Cloud activation uses the original managed sign-in scope. Expired authorization must be
renewed through the original entry; operation IDs alone grant no access.

After activation, `applicationDataVerification` reports the default Source
check as `CHECKING`, `PASSED`, `FAILED`, `EXPIRED`, or `UNKNOWN`. `UNKNOWN` is
not proof that a test failed or that its resources were released. A default
Source failure does not by itself change business readiness. Status reads do
not start a new test; use the permitted connection-test action for an explicit
retry. The default connection remains read-only.

### Confirm recovery

A plan request selects `scope`: `CLUSTER`, `PIPELINE`, or `SHARED_SRS`.
`PIPELINE` requires `pipelineIds`; the shared-capture scope requires
`canonicalChain` and `physicalChain`. Use only the scope offered for the
reported recovery condition. Optional `operationId` and `previousOperationId`
preserve an existing operation or its reported predecessor.

Confirmation requires the returned `operationId`, `planHash`, `controlRevision`,
and `confirmed: true`. A stale plan must be inspected again. Query recovery
status with the original ID; `UNKNOWN` does not establish a successful or
uncommitted result.

Isolate old writers before recovery. Whole-cache recovery leaves affected
pipelines stopped and requires separate full-rebuild confirmation for each.
See [Recover runtime storage](/docs/manage/storage-recovery)
for prerequisites and target-data consequences.

### Export and import configuration

Export accepts `resourceIds`, optional `usernames`, and a `transferKey`.
Use a random 32-byte key encoded as unpadded base64url and retain it separately.
The response includes `transfer` and `defaultSourceId`. The package excludes
runtime state, business rows, drafts, storage bindings, cluster keys, and
owner-bound AI settings.

Import preflight accepts `transfer`, `transferKey`, and `defaultSourceMapping`,
which maps the old default target ID to the destination's existing default
target. It returns `operation` and `preparedTransfer`. Commit with that
operation's `importId`, the returned prepared transfer as `transfer`, and the
same key and mapping. Keep the ID for status queries; inspect the returned
receipt instead of assuming a timeout means the import failed.

Existing resources are not overwritten and imported pipelines do not start.
Cloud rejects packages containing self-hosted accounts. Configuration transfer
operates programmatically between compatible three-layer installations and does
not migrate v0.7 metadata stores. API access does not bypass account or
recovery authorization.

### Locate a materialized collection

`GET /api/views` returns `items` and `unresolved`. Each resolved item identifies
the physical destination with
`location.storeId`, `location.database`, and `location.collection`. Use these
fields to locate stored documents; the View's `id` is its catalog identity,
not necessarily its collection name.

For a managed View, `location.collection` uses the configured
`storage.warm.collection`, or the declared View resource ID when no collection
override is set. This differs from the catalog ID, which includes a pipeline
prefix.
For `serve.sync`, it uses the target name after applying `rename`: an explicit
`map` entry takes precedence; otherwise case conversion applies to the output
table name before the literal prefix and suffix are added. A Nest or Join can
produce a new output name rather than retaining its input table names. For example,
`ACC_COMPOSITE` with `prefix: mysql_` resolves to `mysql_ACC_COMPOSITE` without
changing the catalog ID. In Cloud, collection statistics use this resolved
location as well. See [View and Serve](/docs/reference/view-and-serve).

An output can be listed before its collection exists. `documents`, `sizeBytes`,
and `location.database` can be unavailable; a missing statistic is not zero.
The catalog describes configured output locations, not proof that a run wrote
records there.

Each `unresolved` entry contains `pipelineId`, `code`, and `params`. The server
keeps independently resolved outputs visible when another branch cannot be
resolved. Do not treat a partial or empty `items` list as a complete inventory
while diagnostics remain. Check the named pipeline's source selection,
discovered schema, and referenced definitions, then refresh the list.

`GET /api/pipelines/{id}` also includes `outputTargets`, with `outputs` and
`unresolved`. Each output reports its writing `element`, `kind`, target
`connection`, physical `table`, and catalog `identity`. Use these coordinates
instead of reconstructing a collection name from the pipeline ID or input table.

### View observation fields

Each View's `status` separates the event measurement from the availability of
runtime observations:

| Field | Meaning |
|---|---|
| `state` | `not-loaded`, `loading`, `fresh`, or `stale`. `fresh` means usable current observations, not verified data accuracy. |
| `eventAgeSeconds` | Age of the last target-confirmed source event, taking the maximum across this output's input tables. Can be unavailable. |
| `observedAt` | Time of the observation supporting the result. |
| `refreshedAt` | Time the server assembled this response. |
| `observationAgeSeconds` | Age of the observation, independent of event age. |
| `unit` | `s` for age measurements. |
| `aggregation` | `max-input-table-event-age`. |
| `reason` | Why the state was selected, such as `observation-stale`, `pipeline-inactive`, `measurement-unavailable`, or `clock-or-time-unavailable`. |

Event age grows during source idleness and is not an end-to-end latency or
backlog measurement. A new `refreshedAt` does not make an old observation
current. Keep missing measurements distinct from zero. The compatibility
fields `behindSeconds` and `staleSeconds` describe event age for a `fresh`
state and observation age for a `stale` state respectively.

## Read data through a declared source

The data-browser endpoints inspect the data behind an existing source. Each
request resolves the source's configured connection; callers cannot supply a
database URI, database name, or database-native query command.

> **Data access boundary:** These endpoints are read-scoped, but they can
> return source records and do not create audit events in this preview. There
> is no separate data-browser permission, so any authenticated caller with
> read access can use them. Keep the REST control plane off untrusted networks,
> use HTTPS for remote access, and issue a dedicated read-scoped token to each
> integration.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/sources/{sourceId}/collections` | List collections held by a declared source's database. |
| `GET` | `/api/sources/{sourceId}/collections/{collection}/stats` | Read connector-reported metadata for one collection. |
| `POST` | `/api/sources/{sourceId}/collections/{collection}:find` | Read a bounded preview of rows from one collection. |

Collection listing returns the database's actual collections, not only
resources declared in a workspace. The `stats` response can include
`numOfRows`, `storageSize`, and `avgObjSize`; unavailable values are not zero.
`numOfRows` is an estimate from connector metadata rather than a counted total.

The `find` request body is optional. It can contain `filter`, `sort`, and
`limit`:

```json
{
  "filter": {
    "field": "status",
    "op": "eq",
    "value": "paid"
  },
  "sort": {
    "field": "total",
    "dir": "desc"
  },
  "limit": 25
}
```

`filter` is either one `{field, op, value}` term or one `all` or `any`
combination of terms. Supported operators are `eq`, `ne`, `gt`, `gte`, `lt`,
`lte`, `in`, `exists`, and `contains`. `in` requires a non-empty list,
`exists` requires a Boolean value, and `contains` requires text. The API rejects
database-native operators and arbitrary nested Boolean groups.

Use `asc` or `desc` for `sort.dir`. A literal dotted field name must escape the
dot in the JSON value, for example `"price\\.usd"`. Such a field can be
filtered but cannot be sorted; the server returns
`data-browser.unorderable-field`.

`find` is a one-shot preview, not a paginated query. The default is 10 rows and
the maximum is 200. The response includes `rows`, `approximateTotal`, and
`moreAvailable`; it has no cursor or next-page token. `approximateTotal` might
be unavailable for a filtered read.

In this preview, row previews are available only for sources that use the
`mongodb` connector. Collection listing and statistics can still be available
for other connectors. A row read against another connector returns
`data-browser.connector-not-browsable`.

### Stream collection changes

Connect to this WebSocket endpoint to stream changes from one collection:

```text
/api/data-browser/{source}/{collection}/tail
```

On a self-hosted server, the WebSocket handshake requires the same bearer
credential as other `/api` requests. To filter the stream, provide the structured filter as URL-encoded
JSON in the `filter` query parameter. Each message contains a `kind` of
`INSERT`, `UPDATE`, or `DELETE`, an `at` timestamp, and any available `before`
or `after` row.

The stream is supported only for MongoDB sources in this preview. It reports
changes as they reach the store, so rapid intermediate updates might not appear
as separate messages. A stream with no displayed change for 10 minutes closes
with `data-browser.follow-idle`; a deleted source or a connector stream failure
also ends the connection with a coded reason.

## Machine-token endpoints

On a self-hosted server, these endpoints require an administrator credential:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/tokens` | Create a machine token with `read`, `write`, or `admin` scope. |
| `GET` | `/api/tokens` | List secret-free token descriptors. |
| `POST` | `/api/tokens/{id}:revoke` | Revoke a machine token immediately. |

The create response returns the bearer value exactly once. Store it in a secret
manager or process environment; later list responses do not return it. Scope is
ordered `read` < `write` < `admin`, and a token can call operations at or below
its own grade.

Create a write-scoped token with an administrator credential:

```bash
curl --fail-with-body --silent --show-error \
  -X POST "$TAPSTATE_URL/api/tokens" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"scope":"write"}'
```

The response has this shape. The `token` value is returned only in this create
response:

```json
{
  "tokenId": "<token-id>",
  "scope": "WRITE",
  "token": "<one-time-bearer-value>",
  "createdAt": "<timestamp>"
}
```

List secret-free token metadata with `GET /api/tokens`. Revoke a token with
`POST /api/tokens/<token-id>:revoke`; revocation returns HTTP `204` and takes
effect immediately.

builds.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/pipelines/{id}/start-checks` | Read the start report without changing desired state. Optional `intent=start` (default) or `intent=rerun` for a fresh load. |
| `POST` | `/api/pipelines/{id}:start` | Evaluate start checks and request `RUNNING` when allowed. |
| `POST` | `/api/pipelines/{id}:stop` | Request a transition to `STOPPED`; requires a `purgeState` request body. |
| `POST` | `/api/pipelines/{id}:pause` | Request a transition to `PAUSED`. |
| `POST` | `/api/pipelines/{id}:resume` | Request a transition to `RUNNING` from `PAUSED`. |

### Delete a pipeline and its draft

Use `DELETE /api/pipelines/{id}` for whole-Pipeline removal. Read both the
applied artifact and its draft first, then supply:

- `If-Match`: the quoted artifact content hash.
- `If-Draft-Match`: the quoted positive draft revision, or the literal
  `"none"` when the read found no draft. Do not omit this header.

The server checks both expectations before removal. A running pipeline is
refused; stop it first and confirm its state. A changed draft reports
`pipeline-draft.revision-conflict`, and a missing or malformed draft precondition
reports `pipeline-draft.precondition-required`.

Deletion coordinates artifact cleanup and draft removal. If a concurrent draft
write or cleanup failure leaves residue, the server reports
`artifact.reclaim-incomplete` with the remaining resources. Re-read the artifact
and draft before deciding what to retry; do not treat this error as either full
success or proof that nothing changed. Use the separate draft endpoint when
you intend only to discard unpublished edits.

### Answer start checks

This contract describes start checks on Cloud and v0.8 self-hosted servers. Use
the original report and resource revision when answering a finding.

A start requiring a choice or blocked by a finding returns HTTP `409` with the
usual `code`, `params`, and `message`, plus `startChecks`. The report includes
the applied definition's `contentHash` and findings with their offered actions.
Use the exact finding key and action from that report. For example, this is
an illustrative answer that preserves the target:

```http
POST /api/pipelines/orders_pipeline:start
If-Match: "<contentHash-from-report>"
Content-Type: application/json
```

```json
{
  "decisions": [
    {"finding": "<finding-key-from-report>", "action": "keep"}
  ]
}
```

A request with decisions requires a valid `If-Match`: missing/malformed returns
`428`; a changed definition returns `412`. Fetch a fresh report after a
conflict. Each attempt is evaluated again; answers to questions no longer asked
are reported as unused, and a block cannot be overridden by a decision.

A `clear` action, when offered, changes `on_full_load` to `clear` on the writing
element as well as authorizing removal of the target rows before full load.
Definition changes are validated, audited, and synchronized with the Web draft.
The read-only report itself writes neither desired state nor target data.

See [Start checks](/docs/guides/build-a-pipeline#review-start-checks) for load-policy and
shared-definition rules. `lifecycle.pipeline-not-runnable` returns `409`.

Read the
[completed-snapshot restart limitation](/docs/guides/apply-and-run#completed-snapshot-loads)
before using Clear to replace existing data.

### Stop and retain or clear state

Stopping a pipeline requires a JSON body stating whether to clear internal checkpoint offsets and operator state:

```json
{
  "purgeState": false
}
```

- Set `purgeState` to `false` to keep checkpoints and operator state intact so a future start resumes where it left off.
- Set `purgeState` to `true` to purge this pipeline's checkpoint position and operator state so the next start has no position to carry on from (on a dedicated source connection, this restarts from the source beginning; on a shared mining chain where other pipelines are running, shared chain state and initial-load records are preserved while this pipeline starts fresh).
- Omitting the body or `purgeState` returns HTTP `400` with code `lifecycle.purge-state-not-stated`.

Each lifecycle response returns desired state:

```json
{
  "pipelineId": "orders_to_operational_state",
  "targetState": "RUNNING",
  "revision": "<content-hash>"
}
```

The response proves that the intent was accepted. Read observed status and destination data before reporting execution success.

## Pipeline draft endpoints

A draft stores authoring state separately from the published pipeline artifact.
Saving or compiling a draft does not start a pipeline.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/pipeline-drafts` | List draft summaries; accepts optional `offset` and `limit`. |
| `GET` | `/api/pipelines/{id}/draft` | Read the saved draft and its revision `ETag`. |
| `POST` | `/api/pipelines/{id}/draft` | Create a draft; returns `201` and its `ETag`. |
| `PUT` | `/api/pipelines/{id}/draft` | Replace a draft using `If-Match`. |
| `DELETE` | `/api/pipelines/{id}/draft` | Discard a draft using `If-Match`; returns `204`. |
| `POST` | `/api/pipelines/{id}/draft:preview` | Compile the saved draft or an unsaved candidate to an artifact and DSL. |
| `POST` | `/api/pipelines/{id}/draft:publish` | Compile and apply a draft at the stated revision. |
| `POST` | `/api/pipelines/{id}/draft:rebase` | Update the draft's base artifact hash after an explicit conflict review. |

Draft bodies include `pipelineId`, `mode` (`graph` or `wizard`), and the
matching `graph` or `wizard` document. `pipelineId` must match the path. The
server owns revision increments, timestamps, and `updatedBy`.

Draft `ETag` values are quoted positive integer revisions, such as `"3"`.
They differ from artifact SHA-256 hashes. Copy the draft's current `ETag` into
`If-Match` for replacement or deletion. Missing or malformed preconditions
return `428` (`pipeline-draft.precondition-required`); a changed revision
returns `412` (`pipeline-draft.revision-conflict`).

`draft:preview` with no body compiles the current saved revision. A body can
specify `revision`, and optionally `candidate` containing an unsaved draft.
It returns `artifact` and `dsl`, without applying resources or reading data.

Publish with `{"revision":3,"artifactHash":"<current-artifact-hash>"}`.
For a new pipeline, the hash can be `null`. A changed underlying artifact
returns `409` (`pipeline-draft.artifact-conflict`); review the newer artifact
before rebasing with an explicit `revision` and `artifactHash` (string or
`null`). Rebase preserves the draft edits; it does not merge them automatically.
Publishing does not start or restart the pipeline. Discarding a draft does
not delete its published artifact.

## Cloud assistant endpoints

These endpoints require a valid Cloud session cookie. Provider
settings are scoped to the current organization and Cluster. Self-hosted
authentication does not enable these endpoints. For the bundled Web workflow,
see [Build with AI](/docs/guides/build-a-pipeline#build-with-ai). API clients must
handle the stream, review, and draft updates explicitly.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/ai-provider-settings` | Read `configured`, `providerId`, `baseUrl`, and `model`; never returns the API key. |
| `PUT` | `/api/ai-provider-settings` | Save or replace provider settings for this organization and Cluster. |
| `DELETE` | `/api/ai-provider-settings` | Remove this scope's saved provider settings. |
| `POST` | `/api/ai-provider-settings:check` | Check provider access; a successful result is `{"ok":true}` and does not save the settings. |
| `POST` | `/api/pipelines/{id}/draft:assistant` | Stream a response and any validated proposal as `text/event-stream`. |
| `POST` | `/api/pipelines/{id}/draft:assistant-validate` | Validate a candidate against a saved draft revision without saving or starting it. |

Provider inputs are `providerId: "openai-compatible"`, an allowed HTTPS
`baseUrl`, `model`, and `apiKey`. A blank key can reuse this scope's stored key
only for the same provider and endpoint. Changing the endpoint requires a new
key. Provider checks and generation contact the configured external service;
confirm your organization's data and provider policies before sending prompts.

Generation accepts `revision`, `messages`, and optional `focus`. It uses the
saved draft and discovered MySQL/PostgreSQL schemas as context. With no input
selected, it can include up to three available sources and 40 discovered
tables. A larger source/table inventory requires a source and input selection.
Context can be narrowed further when the schema is too large. Candidate tables
must be present in the included schema context, and a proposal cannot replace
an already selected destination Source.

HTTP `200` only opens the event stream: inspect its status, error, finish, and
`data-proposal` events. A response may ask for clarification without returning
a proposal. Failed candidate validation can also return a request for more
input with diagnostics; do not treat it as an applicable proposal. Closing the
connection cancels generation. A partial response is not an applied change.

Validation accepts `revision` and a complete `candidateWizard` object. Inspect
`valid`, diagnostics, the normalized candidate, and its diff. A stale revision
requires a fresh draft and review. Neither generation nor validation saves the
proposal, publishes the pipeline, or starts it; the client must separately
perform the appropriate draft and lifecycle operations.

## Schema evolution and derived schema endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/pipelines/{id}/derived-schema` | Compare recorded, derived, and target column models across pipeline steps. |

`GET /api/pipelines/{id}/derived-schema` returns a list of step reports comparing three column models:

- `recorded`: The schema previously recorded for that step (omitted for uninferrable steps such as custom scripts).
- `derived`: The current schema worked out from stored discovery models through transforms.
- `target`: The column layout declared on the destination table.

`POST /api/pipelines/{id}:accept-derived-schema` copies stored source discovery models into the pipeline definition and adopts the derived columns as the baseline for future runs (run source schema discovery first when upstream database structures change). Attempting to accept a derived schema while the pipeline is active is rejected with HTTP `500` (`actuation.schema-sync-while-running`).

## Observation endpoints

| Method | Path | Boundary |
|---|---|---|
| `GET` | `/api/pipelines/{id}/status` | Lifecycle intent, display phase, and available runtime observation |
| `GET` | `/api/pipelines/{id}/metrics` | Open metric map, optional `targetAckedPosition`, `positionsNotCollected`, and structured measurement `facts` |
| `GET` | `/api/pipelines/{id}/metrics/history` | Bounded output-rate and selected-table lag history |
| `GET` | `/api/pipelines/{id}/explain` | Explanation derived from current observation evidence |
| `GET` | `/api/pipelines/{id}/snapshot` | Legacy per-table snapshot progress and optional current-run `initialLoad` |
| `GET` | `/api/pipelines/{id}/logs` | Bounded node-local log tail |

The status response separates lifecycle intent from runtime evidence:

| Field | Meaning |
|---|---|
| `state` | Observed lifecycle state, or `NEW` before the first runtime observation. |
| `desiredState` | Requested lifecycle intent, when one exists. |
| `displayState` | Catalog display phase, including `DRAFT`, `NOT_STARTED` (Cloud), and `STARTING`. |
| `hasArtifact` | Whether a published pipeline artifact exists. |
| `observedState`, `observedAt`, `observedAgeMillis` | Runtime state and its age; omitted before the first observation. |
| `failure` | Observed failure with `code`, `params`, and `message`; omitted when absent. |
| `plan`, `awaitingRebalance` | Execution-plan details and pending placement changes, when available. |

A saved draft can have `displayState: "DRAFT"` and `hasArtifact: false`.
In Cloud, an applied pipeline with catalog state `NEW` has
`displayState: "NOT_STARTED"`; its runtime `state` remains `NEW` until observed.
A start request can produce `displayState: "STARTING"` while `state` is still
`NEW`. Metrics, snapshot, and explain require an applied pipeline and a runtime
observation. An applied pipeline without an observation returns
`monitor.no-observation`; a draft without a published artifact returns
`lifecycle.unknown-pipeline`.

The snapshot response retains its `snapshot` map and can additionally include
`initialLoad`:

| Field | Meaning |
|---|---|
| `runKey`, `observedAt` | Execution binding and time of the progress observation. |
| `readMode` | `snapshot_and_cdc`, `snapshot_only`, or `cdc_only`. |
| `phase` | `SNAPSHOTTING`, `MIXED`, `STREAMING`, `COMPLETED`, or `UNKNOWN`. |
| `landedTables`, `totalTables` | Target-confirmed tables and the complete set requiring initial loading in this execution. |
| `tables` | Per-table `stage` (`PENDING`, `READING`, `LANDING`, or `LANDED`), nullable `rowsRead`, and nullable `rowsTotalEstimate`. |

Treat absent `initialLoad` and unknown counts as unavailable. Source reading
can finish before the target confirms delivery. An estimate is not a completion
receipt, and this display projection cannot be used as recovery state.
Completed snapshot-only runs can retain final facts after plan cleanup; stale
or mismatched executions must not inherit another run's progress. See
[Read snapshot progress](/docs/self-hosted/observe-pipelines#read-snapshot-progress).

WebSocket endpoints:

| Path | Behavior |
|---|---|
| `/api/pipelines/{id}/status/watch` | Emits status when the observed state changes. |
| `/api/pipelines/{id}/logs/follow` | Emits newly observed node-local log lines. |

On a self-hosted server, the WebSocket handshake uses the same bearer header.
It returns HTTP `401` or `403` instead of upgrading when authentication or
authorization fails.

Status watch waits for runtime observations; it does not invent a first frame
for a known but unobserved pipeline. An unknown pipeline is refused with a
coded error.

### Pipeline history

`GET /api/pipelines/{id}/metrics/history` accepts:

| Parameter | Required | Contract |
|---|---|---|
| `from` | Yes | Inclusive RFC3339 timestamp with a UTC offset. |
| `to` | Yes | Exclusive RFC3339 timestamp with a UTC offset; later than `from`, at most 15 days apart. |
| `resolution` | No | `auto` (default), `raw`, `PT5M`, `PT30M`, `PT1H`, `PT3H`, or `PT6H`. |
| `limit` | No | Page point budget, 1–1000; default 240. |
| `table` | No | Repeat for each table whose lag is needed; at most 20. Omit for output rates only. |
| `cursor` | No | Opaque `nextCursor` from the preceding page of the same query. |

For example, with a bearer token held in `TAPSTATE_TOKEN`:

```bash
curl --fail-with-body --get "$TAPSTATE_SERVER/api/pipelines/orders/metrics/history" \
  -H "Authorization: Bearer $TAPSTATE_TOKEN" \
  --data-urlencode 'from=2026-09-29T01:00:00Z' \
  --data-urlencode 'to=2026-09-29T02:00:00Z' \
  --data-urlencode 'resolution=PT5M' \
  --data-urlencode 'table=orders' \
  --data-urlencode 'table=shipments'
```

Set `TAPSTATE_SERVER` to your server's HTTP or HTTPS base URL. Use a range
containing your pipeline run.

The response includes the requested and effective ranges, `retentionCutoff`,
`effectiveResolution`, `status`, `consistency`, `segments`, `gaps`,
`unavailable`, and nullable `nextCursor`. Rates describe target-confirmed
records and bytes. The table `lag` series measures the age of the newest
source event confirmed by the target, in seconds. It grows during source
idleness and does not measure end-to-end latency. Do not turn gaps, counter
resets, or unavailable values into zeroes.

`NO_RETAINED_SAMPLES` can be a successful empty result. Samples default to a
60-second interval and 15-day retention. Pagination is `EVENTUAL`: it is not
a frozen audit snapshot. To continue, repeat all query parameters unchanged
and add `cursor`. A signed cursor lasts 10 minutes; `nextCursor: null` ends
the walk.

| Code | HTTP | Response |
|---|---:|---|
| `control.malformed-request` | 400 | Correct the time range, resolution, or limit. |
| `monitor.invalid-cursor` | 400 | Repeat the original query with its cursor, or start a new query. |
| `monitor.cursor-expired` | 410 | Start a new query without the expired cursor. |
| `monitor.query-budget-exceeded` | 400 | Reduce the range or selected tables; a request can scan at most 25,000 raw samples. |

### Pipeline explanations

`GET /api/pipelines/{id}/explain` interprets the current observation. It does
not run a new pipeline or inspect every target row. `NO_MATCH` means no
explanation rule matched. Missing observations return
`monitor.no-observation`; see [Observe a pipeline](/docs/guides/observe-a-pipeline).

### Cluster topology

| Method | Path | Boundary |
|---|---|---|
| `GET` | `/api/cluster/members` | Authenticated cluster membership and pipeline placement read |

The response contains `clusterId`, nullable `topologyRevision`, `members`,
and `pipelines`. Pipeline placement is included in this response; there is no
separate pipeline topology endpoint. A missing revision means unknown, not
revision zero. A refused read is not an empty healthy cluster. See
[Configure a cluster](/docs/guides/cluster).

## Error responses

Coded failures use:

```json
{
  "code": "lifecycle.illegal-transition",
  "params": {
    "from": "RUNNING",
    "verb": "start"
  },
  "message": "..."
}
```

Treat `code` as the stable machine key. `message` is reader-facing and can change.

`engine.job-failed` is a pipeline failure code, not a request-level HTTP error.
When it appears as `failure.code` in a status response or status watch frame, it
means that the pipeline stopped because its job failed. Inspect
`failure.message` and the pipeline logs for the underlying cause.

Common status mappings:

| HTTP status | Typical meaning |
|---:|---|
| `400` | Malformed JSON, DSL validation failure, or a request rejected as bad input |
| `401` | Missing, invalid, expired, or rejected credential |
| `403` | Authenticated but insufficient scope |
| `404` | Artifact, source, connector, pipeline, test result, schema, or observation not found |
| `409` | Closed bootstrap, an illegal/incompatible lifecycle state, or an artifact refusal such as `artifact.in-use` |
| `412` | Source or artifact content hash, or draft revision, is stale |
| `428` | An update, delete, or start carrying decisions omitted a valid version precondition |
| `500` | Coded server or connector failure without a client-attributable mapping |

### Artifact errors

Artifact edits and deletions use a shared `artifact.*` error domain:

The `GET /api/artifacts/{id}` read path currently returns HTTP `404`
without a structured error body when the ID is absent. Handle the HTTP status
first and do not require an `artifact.not-found` JSON envelope for that read;
the coded error is used by artifact mutation/precondition paths.

| Code | Meaning |
|---|---|
| `artifact.not-found` | The requested artifact does not exist. A delete that already succeeded returns this code if it is attempted again. |
| `artifact.precondition-required` | The request did not provide a valid version precondition (`428`). |
| `artifact.version-conflict` | The supplied content hash is stale (`412`). |
| `artifact.in-use` | Another resource still refers to the artifact (`409`). |
| `artifact.pipeline-not-stopped` | The artifact's pipeline is not stopped, so removal is refused (`409`). |
| `artifact.reclaim-incomplete` | The deletion succeeded, but dependent cleanup did not finish. Do not retry the deletion. Record the `reason` and `residue` parameters and contact the server operator; a retry returns `artifact.not-found`. |

### Lifecycle and execution errors

| Code | Meaning |
|---|---|
| `lifecycle.purge-state-not-stated` | A stop request omitted the mandatory `purgeState` boolean field (`400`). |
| `lifecycle.illegal-transition` | The requested transition is forbidden from the pipeline's current lifecycle state (`409`). |
| `lifecycle.incompatible-revision` | The pipeline's target revision is older than its latest applied revision (`409`). |
| `position.write-back-while-live` | Attempted to update checkpoint positions while a pipeline reading the chain is active (`409`). |
| `position.chain-not-read` | The position document specifies a chain not consumed by this pipeline (`400`). |
| `position.field-not-editable` | An immutable position attribute other than `resumeFrom.token` (such as `resumeFrom.epoch` or `resumeFrom.seq`) was altered (`400`). |
| `actuation.schema-sync-while-running` | Attempted to accept a derived schema while the pipeline is active (`500`). |

Unexpected server errors can return HTTP `500` without the coded envelope.
Preserve the status, response body, method, path, and tapstate version when
reporting one.

## Version boundary

- The preview supports both interactive connected sessions and one-shot connected
  commands seeded with `-c` and `-u`, plus explicit creation and exchange of a
  revocable user session.
- No `v1` compatibility freeze exists yet; the Cluster control-plane API uses unversioned `/api/**` routes, separate from the Cloud organization console's `/v1/api/**` service.
