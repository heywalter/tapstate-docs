Tapstate resources are described by the `version: tapstate/v1` declarative
contract. In tapstate Cloud, the visual [Pipeline builder](/docs/guides/build-a-pipeline)
generates and publishes these resources for you (select **Inspect Plan** in
**Build** to view **DSL Preview**). On a local workspace or self-hosted server,
author each resource as a YAML file named `*.tap.yml`.

Use the Schema and connector catalog bundled with the same tapstate version as
your CLI or server. This site does not yet publish a stable, versioned Schema URL.

## Workspace layout

The canonical workspace layout groups files by resource kind:

```text
tap-work/
├── source/
├── pipeline/
├── transform/
├── view/
└── serve/
```

`tapstate add <kind>` writes `<workspace>/<kind>/<id>.tap.yml`. `tapstate validate`
accepts a workspace directory or one resource file.

## Resource kinds

| Kind | Declares |
|---|---|
| [`source`](/docs/reference/source) | A connector connection. A read source includes `mode`; a target connection omits it. |
| [`pipeline`](/docs/reference/pipeline) | Source references, ordered transform steps, and optional view and serve surfaces. A declared view materializes to managed state; serve delivers externally. |
| [`transform`](/docs/reference/transforms) | Reusable transform logic without input wiring. |
| [`view`](/docs/reference/view-and-serve) | Reusable materialization settings without input wiring. |
| [`serve`](/docs/reference/view-and-serve) | Reusable `sync`, `query`, and `push` declarations without input wiring. |

A string reference resolves by resource ID. Top-level IDs must be unique in the
workspace and cannot contain `.`.

The transform reference includes [Unwind](/docs/reference/transforms#unwind)
for expanding arrays into keyed rows. Inline and reusable Views can declare
[write and full-load policies](/docs/reference/view-and-serve#view-write-and-full-load-policies).
Use these fields only with a matching server and schema version.

## Minimal runnable shape

The released preview path uses MySQL and PostgreSQL source connections and one
pipeline:

```yaml title="source/orders.tap.yml"
version: tapstate/v1
kind: source
id: orders
connector: mysql
mode: cdc
config:
  host: mysql
  port: 3306
  database: appdb
  username: ${MYSQL_USER}
  password: ${MYSQL_PASSWORD}
tables: [orders]
```

```yaml title="source/shipments.tap.yml"
version: tapstate/v1
kind: source
id: shipments
connector: postgres
mode: cdc
config:
  host: postgres
  port: 5432
  database: appdb
  schema: public
  user: ${POSTGRES_USER}
  password: ${POSTGRES_PASSWORD}
tables: [shipments]
```

```yaml title="pipeline/orders-sync.tap.yml"
version: tapstate/v1
kind: pipeline
id: orders-sync
source: [orders, shipments]
settings:
  read_mode: snapshot_and_cdc
transforms:
  - id: order-document
    type: nest
    from:
      order: orders
      shipment: shipments
    root:
      from: order
      key: [id]
      embed:
        - from: shipment
          on:
            order_id: id
          as: array
          path: shipments
          arrayKey: [id]
view:
  id: order_state
  from: order-document
  primary_key: id
```

Apply the source connections first, run `discover-schema` for each source, then
apply the complete workspace and start the pipeline. Add expressions that read
`after.<field>` or `before.<field>` only after discovery has supplied the field
types used during server-side validation.

For the complete field shapes, see [source](/docs/reference/source),
[pipeline](/docs/reference/pipeline), [transforms](/docs/reference/transforms),
and [view and serve](/docs/reference/view-and-serve).

## Declaration and execution are different checks

The v1 Schema describes what can be declared. The current preview runtime
executes a smaller subset. A pipeline may declare a view, a serve surface, or
both; a view-only pipeline still materializes records and does not need `serve`.

| Surface | Schema/validator | Current preview runtime |
|---|---|---|
| Resource kinds | `source`, `pipeline`, `transform`, `view`, `serve` | The local quickstart declares `source` + `pipeline` with an inline `view`. |
| Transforms | `filter`, `map`, `js`, `union`, `unwind`, `nest`, `join` | `filter`, `map`, `js`, `union`, `unwind`, and `nest` are wired. `join` is wired in preview under `engine: builtin` with a single driving fact source, unique dimension keys, and no fan-out. |
| Serve declarations | `sync`, `query`, `push` | `serve.sync` delivers to an external target; the local quickstart's managed view does not need a `serve` block. Do not infer an executable runtime surface from Schema acceptance alone. |
| Connector fields | Connector-specific keys are allowed structurally; known catalog fields can receive additional checks. | A catalog entry does not prove that a connector artifact is installed, registered, or available in the current release. |

## Validation model

Offline validation checks:

1. YAML and Schema structure;
2. cross-file ID and reference closure;
3. rules exposed by the bundled connector catalog.

Validation does **not** connect to an external system, verify credentials or
network access, install a connector artifact, or prove that a Schema-declared
feature is executable by the current runtime. Unknown connector-specific config
keys can pass the current offline validator, so test the real connector path
before relying on a configuration.

## Quote regular-expression table selectors

Quote a table-selector regex when it contains YAML flow indicators such as `?`
or `:`. This includes negative lookahead expressions:

```yaml
tables:
  - "/^(?!timezone_test$).*/"
```

The equivalent flow form is `tables: ["/^(?!timezone_test$).*/"]`. Keeping the
regex quoted preserves it as one string and ensures that canonical YAML returned
by tapstate remains parseable. Do not rely on an unquoted scalar for these
patterns, even if a YAML parser happens to accept the input form.

## Compatibility rules

- In v0.7, configure parallelism and batching with node-level `execution`.
  The legacy pipeline `settings.parallelism` and `settings.batch_size` fields
  still parse but have no runtime effect. See [Node execution](/docs/reference/pipeline#node-execution).
- Unknown top-level fields are rejected. Views no longer accept `schema:` in
  v0.6; remove the block from local resources before applying them.
- In self-hosted deployments, a Nest accepts `state.database` for durable state
  placement; Cloud manages Nest state in Durable cache and rejects authored
  `nest.state` (`control.state-database-unavailable`). `as: flat` embeds fields
  without a wrapper. See [Transform reference](/docs/reference/transforms#nest)
  for cardinality, field collisions, and migration requirements.
- Each Join alias must resolve to one physical table, not a transform step or
  table pattern. See [Join input restrictions](/docs/reference/transforms#join-input-restrictions).
- Source `config` accepts connector-owned fields, and `experimental` accepts
  unversioned extension fields. `options` maps are reserved for engine-owned
  options and have an empty vocabulary in this release; non-empty keys fail
  validation with `dsl.unknown-field`.
- `experimental` fields do not carry the v1 compatibility guarantee.
- Use the Schema and catalog from the same release as the runtime you deploy.
