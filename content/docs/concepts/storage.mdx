A pipeline needs its configuration, recovery state, and output to serve
different purposes. Both tapstate Cloud and self-hosted v0.8 installations use
three separate databases for these layers; for the older v0.7 self-hosted
metadata layout, follow its [backup and upgrade guide](/docs/guides/upgrade-to-v0-7).

| Layer | What it retains | Why it matters |
|---|---|---|
| Configuration | Cluster identity, keys, storage bindings, authored resources, connector credentials, and self-hosted accounts | Defines the installation and protects its saved configuration. |
| Durable cache | Sessions, runtime ownership, checkpoints, replay data, discovered models, and operator state | Supports processing and recovery. Losing it requires explicit recovery and full rebuilds. |
| Application data | Records written through the default target Source | Holds the output read by applications; use the database's own backup policy. |

Cloud supplies Configuration; you connect Atlas databases for Durable cache and
Application data. Self-hosted v0.8 setup configures all three databases during
installation. Initial setup tests Durable cache before saving, then activates
the runtime in the same process without requiring a restart. The default
Application data connection is checked asynchronously in the background; being
able to sign in does not establish that it is ready for pipeline output. Use
different database names and retain their original binding. See
[Connect storage](/docs/quickstart#2-connect-storage) or
[Initialize storage](/docs/guides/bootstrap-and-auth#initialize-storage).

The v0.7 self-hosted metadata-store settings (`dataVersion: 12`) do not
configure three-layer Cloud or v0.8 storage, and there is no automatic
migration between the layouts. See [Upgrade to v0.8](/docs/guides/upgrade-to-v0-8).

## Operational state and analytical history

Operational consumers usually need the latest valid state of an account, order, inventory item, or entitlement. Analytical systems usually retain a longer history optimized for scans, aggregation, and model training.

| Concern | Operational state | Analytical history |
|---|---|---|
| Primary question | What is true now? | What happened over time? |
| Common access | Key lookup, current view, event reaction | Scan, aggregate, compare periods |
| Update pattern | Continuous changes and deletes | Batch or append-oriented ingestion |
| Failure sensitivity | Stale state can affect an action | Delayed data usually affects analysis timing |

The two are complementary. A production design can maintain current state for applications while retaining approved history in a warehouse or lake.

## Working state

The data plane needs short-lived state for active processing, buffering, routing, and lookups. Working state improves throughput, but it must not be the only copy of information required after restart.

## Recovery state

Durable cache retains checkpoints, runtime ownership, discovered models,
operator state, and the shared change log. Configuration retains the authored
pipeline and connection definitions. Neither database replaces the other.

Compatible pipelines can share one capture while retaining independent consumer
positions and initial-load boundaries. A restart can continue from retained
positions, but records may be replayed. Snapshot-only reads have no CDC
continuation position.

For shared capture, a source acknowledgement means the change is durable in
tapstate's log; target acknowledgement is recorded separately for each
consumer. Direct capture acknowledges progress after target confirmation.
See [Initial loads and recovery](/docs/concepts/capture-modes#initial-loads-and-recovery).

Keep source logs long enough for recovery. Delivery remains at-least-once for
changes read by the connector; the snapshot-to-stream positioning window can
still miss changes. See [v0.7 limits](/docs/releases/v0.7#known-limits-and-issues).

In a self-hosted deployment, a Nest's `state.database` can select an
authorized database on the Durable cache connection (v0.8) or MongoDB store
connection (v0.7); it must not name Configuration, Application data, or a
system database, and changing the name does not migrate existing state. Cloud
manages Nest state in Durable cache and rejects authored `nest.state`
(`control.state-database-unavailable`).

If the entire cache is lost, [runtime storage recovery](/docs/manage/storage-recovery)
leaves affected pipelines stopped. Confirm each full rebuild separately.
Restoring database connectivity alone cannot reconstruct missing checkpoints.

### Back up configuration and recovery together

Back up Configuration and its original keyring together. Encrypted connector
credentials cannot be restored with a newly generated keyring. A display-only
Source read omits credentials and is not a restorable export.

For self-hosted servers, stop all writers before taking a consistent backup.
Retain Configuration, Durable cache, any separate Nest state databases,
required Application data, and deployment materials such as the installation
directory and custom CA bundles. Protect backups as sensitive credentials, and
restore only into an isolated deployment with old writers stopped. See
[Upgrade to v0.8](/docs/guides/upgrade-to-v0-8) and
[Upgrade to v0.7](/docs/guides/upgrade-to-v0-7).

## Materialized state

Materialized state is the current consumer-facing result. An inline `view`
uses the deployment's default target Source; a `serve.sync` block writes to its
selected target connection.

Three-layer setup creates the default target Source from the Application data
database: `atlas-store` in Cloud, and `views` (default database name
`tapstate_views`) in self-hosted v0.8 installations. Durable cache (default
database name `tapstate_cache` in self-hosted setup) is separate. On an earlier
Cloud layout, **Connect Atlas** configures only the output connection; it does
not replace internal metadata storage.

The disposable local playground can share an unauthenticated MongoDB deployment
between control-plane and application data. Separate database names in that
instance are not a security boundary. Use sample data only; configure access
control, network exposure, and isolation for a deployment you operate.

Its correctness depends on:

- stable keys for updates and deletes;
- defined append or update behavior;
- schema-change policy;
- ordering and duplicate handling;
- reconciliation with the system of record;
- retention and deletion requirements.

For the databases you connect to Cloud, see
[Data security and responsibilities](/docs/manage/data-responsibilities). Server-level backup
and state-placement procedures for v0.7 are in its self-hosted guides.

## Audit history

An audit or replay store answers different questions from a current view. Before retaining change history, define the legal basis, sensitive-field handling, retention period, access policy, and deletion process.

Choose retention, replay, and recovery settings for the workload and deployment you operate. A current-state destination does not automatically provide long-term history.
