Tapstate stores configuration, recovery state, and application output in three
separate MongoDB-backed databases so each layer can be managed, backed up, and
recovered independently:

| Layer | What it stores | Why it matters |
|---|---|---|
| **Configuration** | Cluster identity, keys, storage bindings, authored resources, connector credentials, and local accounts | Defines the installation and protects saved configuration. |
| **Durable cache** | Sessions, runtime ownership, checkpoints, shared change logs, discovered models, and operator state | Supports processing and recovery. Losing it requires explicit recovery and full rebuilds. |
| **Application data** | Records written through the default view target | Holds the output read by applications and follows that database's own backup policy. |

During initial setup, tapstate validates **Durable cache** before saving and
activates the runtime in the same step. It checks the default
**Application data** connection asynchronously in the background, so being able
to sign in does not guarantee the destination is ready for pipeline output.
Keep all three database names distinct and preserve their original bindings.

## Operational state and analytical history

Operational consumers usually need the latest valid state of an account, order, inventory item, or entitlement. Analytical systems usually retain a longer history optimized for scans, aggregation, and model training.

| Concern | Operational state | Analytical history |
|---|---|---|
| Primary question | What is true now? | What happened over time? |
| Common access | Key lookup, current view, event reaction | Scan, aggregate, compare periods |
| Update pattern | Continuous changes and deletes | Batch or append-oriented ingestion |
| Failure sensitivity | Stale state can affect an action | Delayed data usually affects analysis timing |

The two are complementary. A production design can maintain current state for applications while retaining approved history in a warehouse or lake.

## Working state

The data plane needs short-lived state for active processing, buffering, routing, and lookups. Working state improves throughput, but it must not be the only copy of information required after restart.

## Recovery state

Durable cache retains checkpoints, runtime ownership, discovered models,
operator state, and the shared change log. Configuration retains the authored
pipeline and connection definitions. Neither database replaces the other.

Compatible pipelines can share one capture while retaining independent consumer
positions and initial-load boundaries. A restart can continue from retained
positions, but records may be replayed. Snapshot-only reads have no CDC
continuation position.

For shared capture, a source acknowledgement means the change is durable in
tapstate's log; target acknowledgement is recorded separately for each
consumer. Direct capture acknowledges progress after target confirmation.
See [Initial loads and recovery](/docs/concepts/capture-modes#initial-loads-and-recovery).

Keep source logs long enough for recovery. Delivery remains at-least-once for
changes read by the connector; the snapshot-to-stream positioning window can
still miss changes. See [Preview limits](/docs/limits).

If the entire cache is lost, [runtime storage recovery](/docs/manage/storage-recovery)
leaves affected pipelines stopped so you can confirm each full rebuild
separately. Restoring database connectivity alone cannot reconstruct missing
checkpoints.

### Back up configuration and recovery together

Back up **Configuration** together with its original keyring. Encrypted
connector credentials cannot be restored with a newly generated keyring, and
reading a source definition for display omits stored secrets. Before taking a
consistent backup on a server you operate, stop all writers and include
Configuration, Durable cache, any separate Nest state databases, required
Application data, and deployment files (such as the installation directory and
custom CA bundles). Treat backups as sensitive credentials and restore only
into an isolated environment with old writers stopped.

## Materialized state

Materialized state is the current consumer-facing result. An inline `view`
writes to the deployment's default **Application data** target, while a
`serve.sync` block writes to its selected external target connection.

Its correctness depends on:

- stable keys for updates and deletes;
- defined append or update behavior;
- schema-change policy;
- ordering and duplicate handling;
- reconciliation with the system of record;
- retention and deletion requirements.

## Audit history

An audit or replay store answers different questions from a current view. Before retaining change history, define the legal basis, sensitive-field handling, retention period, access policy, and deletion process.

Choose retention, replay, and recovery settings for the workload and deployment you operate. A current-state destination does not automatically provide long-term history.

## Deployment differences

<Tabs items={["Cloud", "Self-hosted"]} groupId="deployment" persist label="Deployment">
<Tab value="Cloud">

- **Storage provisioning:** Tapstate supplies **Configuration**; you connect MongoDB Atlas for **Durable cache** and **Application data** ([Connect storage](/docs/quickstart#2-connect-storage)).
- **Default view target:** `atlas-store`, backed by your Atlas Application data database.
- **Custom Nest state database:** Managed automatically in Durable cache. Authored `nest.state` blocks are rejected with `control.state-database-unavailable`.
- **Backups and security boundary:** Review [Data security and responsibilities](/docs/manage/data-responsibilities) for what tapstate manages versus what you own in Atlas.

</Tab>
<Tab value="Self-hosted">

- **Storage provisioning:** You bind all three databases on a MongoDB replica set or Atlas cluster during setup ([Initialize storage](/docs/guides/bootstrap-and-auth#initialize-storage)).
- **Default view target:** `views` (defaults to `tapstate_views`, separate from `tapstate_cache`).
- **Custom Nest state database:** Optional `nest.state.database` on the Durable cache connection. It cannot name Configuration, Application data, or a MongoDB system database.
- **Backups and security boundary:** Server operators own backups, keyrings, network isolation, and recovery ([Self-hosting](/docs/self-hosted)).
- **Local playground and upgrades:** The Docker playground uses an unauthenticated MongoDB container for evaluation only, where separate database names are not a security boundary. Upgrading from an older single-store v0.7 layout (`dataVersion: 12`) requires a separate three-layer installation with no automatic migration. See [Upgrade to v0.8](/docs/guides/upgrade-to-v0-8) and [Upgrade to v0.7](/docs/guides/upgrade-to-v0-7).

</Tab>
