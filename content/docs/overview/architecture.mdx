This page separates what you can run today in tapstate Cloud (and the v0.8
runtime) from the product's target logical architecture. The preview covers the
current Capture–Transform–Serve path; the target design describes future
direction and does not mean every component is available or production-ready.

For hosted Cloud provisioning, storage layout, and data ownership, see
[Clusters](/docs/manage/clusters) and
[Data security and responsibilities](/docs/manage/data-responsibilities). If you
run and administer servers yourself, see [Self-hosting](/docs/self-hosted).

## Current preview: control and data path

Tapstate connects relational sources—such as the order, customer, and line-item
tables in the Cloud [Quickstart](/docs/quickstart), MySQL and PostgreSQL in
the [local quickstart](/docs/overview/quickstart), or Oracle, SQL Server, Db2
LUW, and Db2 for i—transforms records with operators such as `nest`, and materializes
operational views in MongoDB Atlas or MongoDB:

<PreviewArchitecture />

### Current preview boundaries

- The web application (**Data Sources**, **Pipeline builder**, **Monitoring**,
  **Logs**, **Views**, and **Data validation**) is the primary interface for
  configuring connections, building pipelines, and inspecting runs.
- Pipelines support `filter`, `map`, `js`, `union`, `unwind`, `nest`, and a
  restricted `join`. See [Transform reference](/docs/reference/transforms) for
  their limits.
- `nest` maintains a document assembled from related source tables.
- An inline `view` materializes the result in your Cloud **Atlas state store**
  (or managed MongoDB store on self-hosted). `serve.sync` writes to an external
  MongoDB or Atlas target connection. `serve.query` and `serve.push` are
  schema-defined declarations that the current preview does not execute.
- On self-hosted deployments, the optional native CLI, REST API, and local MCP
  gateway scaffold and validate `*.tap.yml` workspaces and provide bounded
  operational inspection rather than an application-facing data API.
- Runtime, CLI, and control-plane surfaces remain Preview; command and API
  compatibility can change before a stable release.

### Recovery and scale limits

- Cloud Clusters and self-hosted v0.8 deployments use separate storage layers:
  Configuration (supplied by tapstate in Cloud), **Durable cache**
  (checkpoints, runtime ownership, shared change logs, and Nest operator state),
  and **Application data** on MongoDB Atlas or a MongoDB replica set. In-memory
  working state still has workload-dependent capacity requirements; see
  [State and storage](/docs/concepts/storage).
- Recovery can resume from retained positions and replay unconfirmed records. It
  does not remove the delivery and positioning limits in
  [Preview limits](/docs/limits) and [v0.8 release notes](/docs/releases/v0.8#known-limits-and-issues).
- Self-hosted servers default to one member with opt-in
  [cluster mode](/docs/guides/cluster). A cluster profile is not a
  production-readiness guarantee.

Follow the [Quickstart](/docs/quickstart) to run this path in Cloud, or see
[Self-hosting](/docs/self-hosted) for the local Docker playground and CLI
workflow.

## Target logical architecture

The target design expands this one runnable path into a general data plane and
control plane. It explains the intended product boundaries, not additional
current-preview components.

<TapStateArchitecture />

### Target data plane

Capture establishes an initial state and follows later changes. Transform
applies reviewable shaping and document-assembly rules. Materialize
maintains consumer-oriented state, and Deliver exposes that state through
connector or query surfaces.

The recovery boundary covers source positions, checkpoints, retry state,
schema state, and operational history. The current release implements specific
parts of that boundary; see [State and storage](/docs/concepts/storage) for the
retention and recovery limits.

### Target control plane

The target control plane covers versioned intent, lifecycle and authorization,
status, diagnostics, metrics, audit information, and human- and agent-facing
interfaces over the same deterministic operations.

An AI assistant is a client of those controls, not the source of product truth.
Schema, catalog metadata, runtime state, and authorization decisions remain
authoritative within their own boundaries.

## External-system boundary

Source log retention, network paths, credentials, target constraints, API rate
limits, and broker retention remain part of the deployment. Prepare and monitor
them alongside the tapstate data path.

Use [connector guides](/docs/connectors) for external-system preparation and
[Troubleshooting](/docs/guides/troubleshooting) to isolate authoring,
deployment, and data-movement failures.
