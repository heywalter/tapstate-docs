Tapstate uses a single Capture–Transform–Serve architecture. A control plane
validates and manages connections and pipelines, and a data plane moves source
changes into live operational views.

## Current control and data path

Tapstate reads initial snapshots and ongoing changes from relational databases
such as MySQL, PostgreSQL, Oracle, SQL Server, and IBM Db2. It transforms
records in flight with operators like `nest` and keeps operational views up to
date in MongoDB or MongoDB Atlas. See [Supported connectors](/docs/connectors)
for the full list.

### What runs today

Connections, pipelines, monitoring, logs, views, and data validation are
managed from the web application. Pipelines support `filter`, `map`, `js`,
`union`, `unwind`, `nest`, and a restricted `join` (see
[Transform reference](/docs/reference/transforms)). In particular, `nest`
maintains composite documents built from related source tables so downstream
reads do not need cross-database joins.

Pipeline output goes to one of two targets:

- An inline `view` writes to the deployment's managed **Application data**
  database.
- A `serve.sync` block writes to an external MongoDB or MongoDB Atlas target
  connection.

`serve.query` and `serve.push` are accepted in the resource schema, but the
runtime does not execute them yet. Because tapstate is still in Preview,
commands and APIs may change before a stable release.

### Storage, recovery, and scale

Tapstate splits persistence into three MongoDB-backed databases:
**Configuration** stores cluster identity, keys, connections, and pipeline
definitions; **Durable cache** stores checkpoints, runtime ownership, shared
change logs, and Nest operator state; **Application data** holds materialized
views. Active processing also keeps working state in memory, so memory
requirements scale with workload. See [State and storage](/docs/concepts/storage)
for details.

Pipelines resume from stored checkpoints and may replay unconfirmed records
after a restart. Review [Preview limits](/docs/limits) and the
[v0.8 known limits](/docs/releases/v0.8#known-limits-and-issues) for delivery
and snapshot-to-CDC positioning details. Single-node execution is the default,
with opt-in multi-member [cluster mode](/docs/guides/cluster) when you need to
scale capture.

## Deployment options

Both deployment models run the same engine and data path, but differ in what
tapstate manages versus what you operate.

<Tabs items={["Cloud", "Self-hosted"]} groupId="deployment" persist label="Deployment">
<Tab value="Cloud">

- **Hosting:** Tapstate provisions and upgrades managed Clusters through the [organization console](/docs/manage).
- **Storage:** Tapstate supplies **Configuration**; you connect MongoDB Atlas for **Durable cache** and **Application data**.
- **Connectors:** Standard connectors are pre-staged in **Data Sources** (`db2i` is registered separately).
- **Interfaces:** Author and operate pipelines in the web application, with **Tapstate AI** built into the pipeline builder.

Follow the [Cloud quickstart](/docs/quickstart) to launch a hosted workspace.

</Tab>
<Tab value="Self-hosted">

- **Hosting:** You deploy and upgrade tapstate on your own infrastructure ([Self-hosting](/docs/self-hosted)).
- **Storage:** You initialize and back up all three MongoDB-backed databases ([Initialize storage](/docs/guides/bootstrap-and-auth#initialize-storage)).
- **Connectors:** Administrators seed or register connector JARs on the server ([Register connectors](/docs/guides/register-connectors)).
- **Interfaces:** Use the web workbench, or automate `*.tap.yml` workspaces through the native CLI, REST API, and local MCP gateway.

Follow the [local quickstart](/docs/overview/quickstart) to try the Docker playground.

</Tab>
</Tabs>

## Target logical architecture

The target architecture extends today's preview into a broader control plane
and data plane. Not every source type, delivery surface, or governance control
below is available yet.

<TapStateArchitecture />

### What changes beyond the current preview

- **Broader inputs and delivery surfaces:** Beyond relational databases and
  MongoDB sync, the target data plane covers message brokers, files, and SaaS
  APIs on the input side, and executes `serve.query` and `serve.push` alongside
  materialized views and external syncs.
- **Unified human and agent control:** Versioned pipeline definitions,
  authorization, diagnostics, metrics, and audit history sit behind one control
  plane. AI assistants act as clients of those controls rather than holding
  independent product truth; schemas, connector catalogs, runtime state, and
  authorization rules remain authoritative.

## External-system boundary

Source log retention, network connectivity, credentials, target constraints,
API rate limits, and broker retention remain outside tapstate and must be
managed in your own environment.

See the [connector guides](/docs/connectors) for external-system setup and
[Troubleshooting](/docs/guides/troubleshooting) to diagnose authoring,
deployment, or runtime errors.
