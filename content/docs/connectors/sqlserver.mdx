Connect SQL Server as a source for an initial full load and CDC into
operational state or analytics targets. Complete the database preparation that matches the
read mode you plan to use.

For Cloud version and deployment scope, check [Supported connectors](/docs/connectors#supported-connectors).
Already prepared the database? [Connect it in the Web application](#connect-to-sql-server).

## Before you begin

In Cloud, select the connector in **Data Sources**. Check
[Supported connectors](/docs/connectors#supported-connectors) for the version and deployment
scope, then allow the [Cluster's outbound address](/docs/manage/clusters#prepare-network-access)
through the database's firewall. Complete the read-mode preparation below
before selecting **Test connection**.

Connector registration and host-level setup in this guide apply to self-hosted
servers.

<span id="source" />

Prepare the database for the source read mode you plan to use.

Choose the outcome you need. Each tab is a complete preparation path; you do not need to combine steps from both tabs.

<SourceModeTabs label="Choose the SQL Server source read mode">
<SourceModeTab value="snapshot" label="Full load (Snapshot)" description="Copy existing rows once">

Use **Full load** (`Snapshot`) to copy the rows that exist now. It does not require SQL Server Agent or database/table CDC.

**1. Create a dedicated reader**

Create a login and map it to a user in the source database:

```sql
CREATE LOGIN tapstate
  WITH PASSWORD = 'replace-with-a-secret',
       DEFAULT_DATABASE = database_name;
GO

USE database_name;
GO
CREATE USER tapstate FOR LOGIN tapstate WITH DEFAULT_SCHEMA = dbo;
GRANT CONNECT TO tapstate;
GRANT SELECT ON SCHEMA::dbo TO tapstate;
GO
```

**2. Restrict table access when needed**

Use object-level `SELECT` grants instead of a schema grant when the account should read only a subset of tables.

</SourceModeTab>
<SourceModeTab value="snapshot-cdc" label="Full load + CDC" description="Copy existing rows, then follow table CDC changes">

Use this preparation path when the destination must begin with existing rows,
then follow SQL Server CDC changes.

**1. Start SQL Server Agent and check log capacity**

Make sure SQL Server Agent is running. On Linux, install and enable the Agent service for the SQL Server version in use. Check the transaction log growth limit, available disk space, and the expected number of capture instances before enabling CDC.

**2. Enable database and table CDC**

For SQL Server, enabling CDC on the database requires membership in the `sysadmin` server role. This creates the `cdc` schema. After database CDC is enabled, a member of `sysadmin` or the database's `db_owner` role can enable CDC on individual tables. Run the following as a `sysadmin` account:

```sql
USE database_name;
GO
EXEC sys.sp_cdc_enable_db;
GO

EXEC sys.sp_cdc_enable_table
  @source_schema = N'dbo',
  @source_name = N'orders',
  @capture_instance = NULL,
  @role_name = N'cdc_reader',
  @supports_net_changes = 1;
GO
```

For a table without a primary key, set `@supports_net_changes = 0`.

**3. Create a dedicated CDC reader and grant access**

Create a login, map it to the source database, grant read access to both the source schema and the newly created `cdc` schema, and add the user to `@role_name` (`cdc_reader`) when specified above:

```sql
CREATE LOGIN tapstate
  WITH PASSWORD = 'replace-with-a-secret',
       DEFAULT_DATABASE = database_name;
GO

USE database_name;
GO
CREATE USER tapstate FOR LOGIN tapstate WITH DEFAULT_SCHEMA = dbo;
GRANT CONNECT TO tapstate;
GRANT SELECT ON SCHEMA::dbo TO tapstate;
GRANT SELECT ON SCHEMA::cdc TO tapstate;
GO
```

On SQL Server 2012 or later, add the reader to the CDC role:

```sql
ALTER ROLE cdc_reader ADD MEMBER tapstate;
GO
```

On SQL Server 2008 or 2008 R2, use this statement instead:

```sql
EXEC sp_addrolemember N'cdc_reader', N'tapstate';
GO
```

Run the role assignment in the source database. If you chose a different
`@role_name` when enabling table CDC, use that role name instead of `cdc_reader`.

Use object-level `SELECT` grants when the account should read only a subset of source tables.

**4. Verify the capture instance**

Confirm that CDC is enabled and discover the generated capture instance:

```sql
SELECT name, is_cdc_enabled
FROM sys.databases
WHERE name = N'database_name';

EXEC sys.sp_cdc_help_change_data_capture
  @source_schema = N'dbo',
  @source_name = N'orders';

EXEC sys.sp_cdc_help_jobs;
```

Confirm that both the capture and cleanup jobs are present and running. A missing or stopped capture job means table CDC can be enabled without producing new change rows.

**5. Set the cleanup window**

Set cleanup retention longer than the longest planned outage. The value is in minutes; this example keeps two days:

```sql
EXEC sys.sp_cdc_change_job
  @job_type = N'cleanup',
  @retention = 2880;
```

SQL Server CDC polling cost grows with the number of capture instances. Split very large table sets when one polling cycle cannot meet the required latency.

## Connect to SQL Server

1. Open your Cluster and select **Data Sources** > **Create source**.
2. Select **SQL Server** and enter a **Source ID**.
3. Choose the read mode you prepared, then enter the connection settings below.

   <span id="reference" />
   <span id="connection-settings" />

   [![SQL Server connection form populated with example settings](/images/cloud/sqlserver-form.png)](/images/cloud/sqlserver-form.png)

   The screenshots use fictional connection details. Replace them with your own.
   The settings below include fields outside the captured area and options
   shown only for particular connection modes.
   Configuration keys are included for the alternative CLI/YAML workflow.

   - **Connection settings**

     - **Source ID (`id`)**: A stable ID for the connection, such as `orders_sqlserver`. It cannot be renamed after creation. Required.
     - **Read mode (`mode`)**: `snapshot` for a one-time read, or `cdc` for existing rows and later changes. Complete the matching preparation above. Select before creation.
     - **DB Address (`host`)**: SQL Server instance host address or hostname. Required.
     - **Port (`port`)**: SQL Server service port. Use a numeric integer. Default: `1433`. Required.
     - **DB Name (`database`)**: SQL Server database name. Required.
     - **Schema (`schema`)**: Schema containing the source tables, for example `dbo`. Required.
     - **User (`user`)**: Database account login (also accepted as `username`).
     - **Password (`password`)**: Database account password or secret reference.
     - **CDC Solution (`cdcSolution`)**: CDC capture method: `CT` (native CDC change tables) or `LogParser`. Default: `CT`. Optional.

   - **Advanced settings**

     - **Timezone for Datetime (`timezone`)**: Timezone offset for temporal conversions (e.g. `+00:00`, `+08:00`). Optional.
     - **Use SSL/TLS (`useSSL`)**: Whether to enable SSL/TLS transport encryption (defaults to `false`). Default: `false`. Optional.
     - **SSL/TLS Certificate Password (`sslKeyPassword`)**: Password protecting the client SSL/TLS key. Required when Use SSL/TLS is `true`.
     - **Server hostname (`hostNameInCertificate`)**: Server hostname override used to validate the SSL/TLS certificate. Shown when Use SSL/TLS is `true`.
     - **Other connection string parameters (`extParams`)**: Additional JDBC connection parameters accepted by the Microsoft driver. Optional.

   - **Connection security**: Use the TLS and SSH settings offered by the connector.
     See the [shared transport fields](/docs/guides/manage-data-sources#tls-and-ssh-connections)
     for certificate files and SSH account settings. Keep certificate verification enabled.

   Advanced capture settings require their corresponding database and runtime
   preparation; selecting a different log reader does not install it.

   <span id="additional-catalog-fields" />

   <span id="test-and-save" />

4. Select **Test connection**, review the results, and resolve failed checks.
5. Select **Create source**, then open the saved connection and check its
   discovered tables, columns, and keys.
6. [Build a pipeline](/docs/guides/build-a-pipeline) to select the data and
   destination. Creating a connection does not start data movement.

A passed test confirms only the reported connection checks. Verify the initial
output and subsequent changes for the pipeline you build.

## CLI and YAML

This alternative is for **self-hosted servers**. File generation and validation
can run offline; login, apply, and connection tests require your own server.
Cloud users should use the Web steps above. See [CLI scope](/docs/self-hosted#cli-and-automation).

Use the same [connection settings](#connection-settings) as the Web form.
In YAML, put connector-specific keys under `config`; `id` and `mode` are resource fields.

### Register on a self-hosted server

<span id="connector-availability-and-licensing" />

The SQL Server connector artifact bundles the Microsoft JDBC Driver under the MIT License; commercial connector use remains subject to the applicable agreement. It is distributed as an official preview artifact separate from the base server image. Before applying SQL Server connections on a new or upgraded server, register the connector:

```text
connectors
register sqlserver
```

In production and air-gapped environments, you can also mount the connector JAR into `TAPSTATE_CONNECTORS_SEED_DIR` for automatic boot-time registration. See [When registration is required](/docs/guides/register-connectors#when-registration-is-required).

### Create a connection

Use this alternative when authoring a local workspace. For browser setup,
complete the connection flow above; no local file is required.

Tapstate stores each SQL Server connection as a `.tap.yml` file in the workspace.

Create `tapstate-work/source/orders_sqlserver.tap.yml`. The connection's `mode`
controls its read capability. For a full-load-only source, use `mode: snapshot`
instead of `mode: cdc`.

```yaml title="tapstate-work/source/orders_sqlserver.tap.yml"
version: tapstate/v1
kind: source
id: orders_sqlserver
connector: sqlserver
config:
  host: sqlserver.internal
  port: 1433
  database: orders
  schema: dbo
  user: ${SQLSERVER_READER_USER}
  password: ${SQLSERVER_READER_PASSWORD}
mode: cdc
tables:
  - orders
  - /customers_.*/
```

For a CDC-capable source, use `mode: cdc` after enabling database and table CDC
and confirming that the cleanup window covers the recovery objective.

Before using the pipeline below, add the `operational_state` target connection
from the [MongoDB guide](/docs/connectors/mongodb#create-a-connection) to the
same workspace. This pipeline assumes that target already exists:

```yaml title="tapstate-work/pipeline/orders_to_operational_state.tap.yml" structure-only
version: tapstate/v1
kind: pipeline
id: orders_to_operational_state
source: orders_sqlserver
serve:
  from: /.*/
  sync:
    - id: write_operational_state
      source: operational_state
      write_mode: upsert
      ddl: fail
```

### Validate the configuration

```bash
tapstate validate --workdir tapstate-work
```

Validation does not resolve the host, credentials, or a SQL Server instance. To verify the connection against the database, register the SQL Server connector, apply the workspace, and run `test`:

```bash
tapstate -w tapstate-work
```

```text
connect http://127.0.0.1:8080
login admin
register sqlserver -o json
apply
test orders_sqlserver -o json
```

Then verify in a staging table that:

1. the account can discover and snapshot the table;
2. the capture instance produces insert, update, and delete rows;
3. the cleanup window exceeds the tested recovery time;
4. data types match downstream consumer expectations.

## Limitations

- CDC must be enabled and retained for every participating table. If cleanup removes the saved position, recovery requires a new snapshot.
- Tables with CDC enabled cannot use `TRUNCATE TABLE`, and renaming columns with `sp_rename` is not supported.
- After a schema change, SQL Server does not automatically rebuild the capture instance. Disable and re-enable table CDC during a controlled window before resuming dependent DML.
- DDL and DML close together can create a gap because some implicitly committed DDL is not represented in `cdc.ddl_history`.
- SQL Server CDC processes up to 64 KB for an inserted or updated large field by default. Capture only the required columns when large fields are involved, and verify the effective limit with representative values in staging.
- A task that polls hundreds of capture tables can accumulate latency and load. Split very large table sets and measure the polling interval in staging.
- SQL Server 2005 does not provide native CDC and is not supported for CDC.
- Configure forced encryption on SQL Server when required, then use the connection settings supplied by your tapstate deployment.

### Recreate CDC after a table change

Pause dependent writes or coordinate a maintenance window, then discover the current capture instance, disable it, and enable it again:

```sql
EXEC sys.sp_cdc_help_change_data_capture
  @source_schema = N'dbo',
  @source_name = N'orders';
GO

EXEC sys.sp_cdc_disable_table
  @source_schema = N'dbo',
  @source_name = N'orders',
  @capture_instance = N'dbo_orders';
GO

EXEC sys.sp_cdc_enable_table
  @source_schema = N'dbo',
  @source_name = N'orders',
  @role_name = N'cdc_reader',
  @supports_net_changes = 1;
GO
```

Recreating a capture instance changes the available change-table history. Verify the pipeline's saved position and run an end-to-end reconciliation before resuming production traffic.

## Data compatibility

### Database-side reference

This table summarizes SQL Server data behavior for the connector. Test uncommon
types with representative data before migration.

| Signal | Database-side baseline |
|---|---|
| Versions | SQL Server 2008, 2008 R2, 2012, 2014, 2016, 2017, 2019, 2022 |
| Architecture | Single node |
| Source preparation | Snapshot and CDC prerequisites |
| DDL | Add, rename, alter, and drop columns, subject to CDC limitations |

### Data types

| Family | Database-side baseline |
|---|---|
| Text | `char`, `varchar`, `nchar`, `nvarchar`, `text`, `ntext`, `varchar(max)`, `nvarchar(max)` |
| Integer | `tinyint`, `smallint`, `int`, `bigint` |
| Decimal | `decimal`, `numeric`, `money`, `real`, `float` |
| Date and time | `date`, `time`, `datetime`, `datetime2`, `smalldatetime`, `datetimeoffset` |
| Binary | `binary`, `varbinary`, `varbinary(max)`, `timestamp`/`rowversion` |
| Other | `uniqueidentifier`, `bit`, `image`, `xml`, `geography` |
